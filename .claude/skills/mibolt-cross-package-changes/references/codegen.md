# Code generation from the contract

How `contracts/commerce/openapi.yaml` becomes the shop SDK, the admin client
and the backend interfaces, what `api:generate` and `api:drift` actually do,
and how to read a failure in either. Paths are repo-relative and commands run
from the repository root.

## 1. The two frontend generator configurations

Both run ng-openapi-gen (`frontend/package.json` declares `^1.0.5`, and
1.0.5 is installed) against the same input,
`../contracts/commerce/openapi.yaml`, relative to `frontend/`. They differ in
three keys only:

| Key | `frontend/ng-openapi-gen.json` (shop) | `frontend/ng-openapi-gen.admin.json` (admin) |
|---|---|---|
| `output` | `projects/shop-api/src/generated` | `projects/admin/src/app/api/generated` |
| `apiService` | `Api` | `AdminApi` |
| tag filter | `excludeTags` the four admin tags (`frontend/ng-openapi-gen.json:13`) | `includeTags` the same four (`frontend/ng-openapi-gen.admin.json:13`) |

The shared keys and what each does here. The option meanings are quoted from
the generator's own schema, https://github.com/cyclosproject/ng-openapi-gen/blob/master/ng-openapi-gen-schema.json
(the `$schema` key at `frontend/ng-openapi-gen.json:2` points at the
installed copy), and its README, https://github.com/cyclosproject/ng-openapi-gen:

- `includeTags` / `excludeTags`: "filters the generated services" by tag. The
  tag on an operation therefore decides which client gets it: one of
  `AdminAuth`, `AdminUsers`, `AdminProducts`, `AdminMedia` puts it in the admin
  client only, any other tag in the shop SDK only.
  `frontend/tests/contract/admin-tags.ts:14` holds the same four names as
  `ADMIN_TAGS`, and `frontend/tests/contract/sdk-split.spec.ts:98-101` fails if
  the three lists stop being equal.
- `excludeParameters: ["If-Match"]` (`frontend/ng-openapi-gen.json:12`, `frontend/ng-openapi-gen.admin.json:12`): "ignores on generated
  services any parameters whose names are in this list". Neither client's
  function signatures carry `If-Match`; the callers attach it through an
  `HttpContext` (the contract-change-chain reference, section 8).
- `ignoreUnusedModels: true`: "ignore model files that are not referenced by
  any operation". A schema reachable only from admin operations is not
  generated into the shop SDK, and the reverse: on 2026-09-26 the shop SDK had
  no `admin-*` model and the admin client no cart, checkout, order or
  catalogue model (`Product`, `CatalogItem`).
- `enumStyle: "alias"` and `enumArray: true`: an enum becomes a union type,
  plus "a sibling `.ts` file which exports an array" of its values. A new enum
  value therefore changes two files per client, for example
  `frontend/projects/shop-api/src/generated/models/problem-code.ts` and
  `frontend/projects/shop-api/src/generated/models/problem-code-array.ts`.
- `services: false`, `module: false`, `promises: false`: no per-tag service
  classes and no NgModule; operations are standalone functions returning
  Observables, called through the one service, as
  `this.api.invoke(getCart, {})` does at
  `frontend/projects/storefront/src/app/features/cart/cart.facade.ts:460`.

## 2. What the frontend generator writes

- `functions.ts` re-exports one function per operation, `models.ts` one type
  per schema, and `api.ts` (shop) or `admin-api.ts` (admin) is the service.
- `fn/` holds one directory per tag in kebab case (`fn/cart`, `fn/demo-access`,
  `fn/admin-products`) and one file per operation named after its
  `operationId` in kebab case, so `getCart` is
  `frontend/projects/shop-api/src/generated/fn/cart/get-cart.ts`.
- An operation with several response media types is generated once per type:
  `getMedia` is `getMedia$Jpeg`, `getMedia$Png` and `getMedia$Webp`
  (`frontend/projects/shop-api/src/generated/functions.ts:11-15`). The contract
  tests match an operation id by that `$` prefix
  (`frontend/tests/contract/operation-matrix.spec.ts:117-133`).
- `models/` holds one file per schema, named in kebab case
  (`AddCartItemRequest` is `models/add-cart-item-request.ts`).
- Every file opens with `/* eslint-disable */` and
  `/* Code generated by ng-openapi-gen DO NOT EDIT. */`
  (`frontend/projects/shop-api/src/generated/api.ts:1-2`). ESLint ignores both
  directories (`frontend/eslint.config.mjs:90-92`), Prettier ignores them
  (`frontend/.prettierignore:2-3`), and the admin coverage target excludes its
  client (`frontend/angular.json:371`).
- The shop SDK is a library, `frontend/projects/shop-api/`, whose only
  hand-written source is `frontend/projects/shop-api/src/public-api.ts`; apps
  import the generated files through `@mi-bolt/api/*`
  (`frontend/tsconfig.json:18`). The admin client lives inside the admin app
  and is imported by relative path; there is no alias for it.

Counts on 2026-09-26: 88 tracked files in the shop SDK, 54 in the admin client.

## 3. `api:generate` and `api:drift`, exactly

Both rewrite tracked files under the two generated directories, so they are a
shared resource (`.claude/rules/parallel-spawns.md`, "What a batch shares"):
run them only when your task hands you that step.

- `mise run api:generate` (`mise.toml:76-78`) runs `//frontend:api:generate`,
  which is `npm run api:generate` in `frontend/`: both configs in sequence
  (`frontend/package.json:31`), and `//backend:api:generate`, which is
  `./gradlew :services:commerce:openApiGenerate` (`backend/mise.toml:18-19`).
- `mise run api:drift` (`mise.toml:80-82`) runs only `//frontend:api:drift`,
  which is `frontend/package.json:32`:
  1. `npm run api:generate`, so it regenerates first and leaves the result in
     the working tree;
  2. `git diff --exit-code` over the two generated directories, which compares
     the working tree with the index and exits 1 on any difference
     (https://git-scm.com/docs/git-diff);
  3. `test -z` over `git ls-files --others --exclude-standard` for the same
     directories, which fails on any untracked, not-ignored file there, such
     as a newly generated model nobody added
     (https://git-scm.com/docs/git-ls-files).

  So locally it passes only once the regenerated output is staged or
  committed: after a contract change, running it before staging the new
  output fails by design. In CI, where the checkout has nothing staged, it
  means "the committed clients match the committed contract". Where it runs is
  in SKILL.md, "What fails when a step is skipped".
- The script name itself is pinned: renaming or removing `api:generate` in
  `frontend/package.json` fails `frontend/tests/contract/schema.spec.ts:613-630`.

## 4. The backend generator and its discriminator guard

`backend/services/commerce/build.gradle` wires the OpenAPI Generator Gradle
plugin, version 7.25.0 (`backend/services/commerce/build.gradle:5`), with the `spring` generator:

- `prepareOpenApiSpec` (`backend/services/commerce/build.gradle:67-87`) reads the contract (`backend/services/commerce/build.gradle:65`) and writes a
  derived copy to the build directory's `openapi/openapi.yaml`, flattening four
  single-value enum discriminator properties to plain strings:
  `HomeDeliverySelection.optionId`, `PickupPointSelection.optionId`,
  `CardOrderRequest.paymentMethod` and `CashOnDeliveryOrderRequest.paymentMethod`
  (`backend/services/commerce/build.gradle:50-63`). The reason is an upstream generator bug, recorded with its issue
  link in `backend/docs/decisions/0001-openapi-generator-and-discriminator-workaround.md`.
- **The guard.** Each replacement matches a whole text block, including the
  line after the enum value, and must match exactly once (`backend/services/commerce/build.gradle:73-80`); otherwise
  the task throws "prepareOpenApiSpec: expected the ... block to appear
  exactly once in ..., found N. The spec changed; update the build-time copy
  in build.gradle." It fires when one of those four blocks is edited, a
  property is inserted after `optionId` or `paymentMethod` in them, a second
  enum value is added under one of them, or a schema is inserted between
  `PickupPointSelection` and `DeliverySelection` (the comment at `backend/services/commerce/build.gradle:44-49` says
  so). The blocks sit at `contracts/commerce/openapi.yaml:2713-2736` and
  `contracts/commerce/openapi.yaml:2869-2902`. A new delivery or payment
  option adds a new subtype with its own single-value discriminator, which
  none of the four replacements covers: read decision 0001 before adding one.
- `openApiGenerate` (`backend/services/commerce/build.gradle:89-114`): `interfaceOnly`, `useSpringBoot4`,
  `useTags`, `documentationProvider: none`, `annotationLibrary: none`,
  `openApiNullable: false`, packages `com.example.mi_bolt_backend.api` and
  `com.example.mi_bolt_backend.api.model`. With `useTags` each tag becomes one
  interface, `<Tag>Api`, implemented by one controller, for example
  `CartController implements CartApi`
  (`backend/services/commerce/src/main/java/com/example/mi_bolt_backend/cart/CartController.java:25`);
  decision `backend/docs/decisions/0014-openapi-tags-and-admin-contract.md`
  records why. `skipDefaultInterface` is not set, and its default is `false`,
  "Whether to skip generation of default implementations for java8
  interfaces" (https://openapi-generator.tech/docs/generators/spring), so the
  interfaces carry default methods and an operation no controller overrides
  still compiles.
- The output directory is deleted before each run (`backend/services/commerce/build.gradle:119-127`), so a removed
  schema leaves no stale class; it is added to the main source set
  (`backend/services/commerce/build.gradle:129-135`), and every Java compile depends on generation (`backend/services/commerce/build.gradle:137-139`).
  The `test` and `integrationTest` tasks declare the contract as an input
  (`backend/services/commerce/build.gradle:142`, `backend/services/commerce/build.gradle:149`), so a contract change reruns them.
- The generated packages are excluded from JaCoCo (`backend/services/commerce/build.gradle:167-170`) and from
  `pmdMain` (`backend/services/commerce/build.gradle:244`).
- The backend image build copies the contract in through the `contracts`
  build context (`deploy/compose.yaml:33-34`,
  `backend/services/commerce/Dockerfile:14`), so the image generates from the
  same file.

## 5. When regeneration or drift misbehaves

- **`api:drift` red locally after a contract change.** Expected until the
  regenerated output is staged with the contract change; SKILL.md, fan-out
  step 6, says who stages it. Rerun once it is.
- **`api:drift` red in CI.** The committed clients do not match the committed
  contract: the contract changed without a regeneration, a generated file was
  edited by hand, or a generated file was never added. The fix is to
  regenerate and have the result committed with the contract, never to edit
  the generated file. When the red run follows a rebase that changed
  `frontend/package-lock.json`, compare the version in
  `node_modules/ng-openapi-gen/package.json` in `frontend/` with the
  lockfile's `node_modules/ng-openapi-gen` entry before regenerating: CI
  installs with `npm ci` (`.github/workflows/frontend.yml:155`), so it
  generates with the locked version. Bringing the local install in line
  rewrites the `node_modules` every worktree shares, so it is one agent's at a
  time (`.claude/rules/parallel-spawns.md`, "What a batch shares").
- **A model you expected is missing from one client.** `ignoreUnusedModels`
  drops a schema no operation of that client references; check which tag the
  operations using it carry.
- **The backend build fails in `prepareOpenApiSpec`.** The message names the
  block and says what to do: update that entry's `from` and `to` text in
  `backend/services/commerce/build.gradle:50-63` to the new block, so each
  block still matches exactly once. A second enum value under a discriminator,
  or a fifth discriminated subtype, is not a text update: read decision 0001
  first (section 4).
- **A new backend endpoint answers without its implementation running.** The
  controller does not override the new interface method, and the generated
  default method answers instead (section 4); the backend work belongs to
  `mibolt-commerce-backend`.
