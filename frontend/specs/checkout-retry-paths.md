# MiBolt checkout retry-paths test plan

## Application Overview

MiBolt is a Hungarian demo storefront: an Angular application served from the Playwright base URL with the in-page MSW mock behind it, so there is no backend and no database, and every product, price, order and payment is demo data. The purchase path is the phone listing `/telefonok`, the product page `/telefonok/<slug>`, the cart `/penztar/kosar`, the checkout wizard `/penztar/adatok` -> `/penztar/szallitas` -> `/penztar/ellenorzes` -> `/penztar/siker/<orderId>`.

This plan carries the four rows of the standard whose fault fires once and whose second attempt succeeds, quoted from `docs/spec/test-scenarios.md` as action -> required assertion:

- E068 "Save contact then Retry" -> "Typed values retained; no advance on failure."
- E080 "Fail choices load then Retry" -> "No fabricated choice or zero shipping; retry recovers."
- E100 "Fail before commit then Retry" -> "One eventual order; exact request/key reused for uncertain transport failure."
- E103 "Fail GET then Retry" -> "Existing receipt restored; no new transaction."

Each row is driven by the mock's once-only fault family, whose operation names are listed in `FAULT_OPERATIONS` and whose responses are built in `faultResponse`: `?mi-scenario=fail-once-<operation>` answers the first matching request of the page load with a 503 problem, `?mi-scenario=offline-once-<operation>` fails it as a network error, and every later request is served, so the screen's own retry recovers. The always-failing variants of these same four operations are `specs/checkout-fault-paths.md`; nothing of that plan is repeated here, and the happy paths are `specs/storefront-integration.md`.

Three facts govern every scenario. First, each test starts in a fresh browser context and the mock keeps its state (cart, checkout draft, order counter, receipts) in that context's `sessionStorage` under a key that carries the scenario name, so one fresh context is an empty cart and the scenarios are independent and can run in any order. Second, the mock reads `?mi-scenario=<name>` when the document loads and remembers it for the tab: an in-app navigation keeps the scenario although the address bar drops the query, and a `page.goto` without the query resumes the scenario the tab loaded last (`?mi-scenario=default` switches back), so a scenario opens its first page with the query and keeps it on every goto. Third, a "once" fault arms again on every page load of the scenario, a `page.goto` without the query included, but not on a retry inside the page, because the browser builds one handler list per page load.

Two places where a row asks for something the screen does not offer, and what the screen does instead.

E068's row asks for "Typed values retained; no advance on failure." The delivery step renders no contact summary: `/penztar/szallitas` holds `delivery-options`, `payment-selector`, the billing block and its own `delivery-summary`, and no contact control at all — no contact input and no contact summary element exists on it. The wizard's contact summary is the review page's "Kapcsolattartási adatok" card, `review-contact`, so scenario 1.1 completes the delivery step and asserts the typed values there. No control is invented for the delivery step.

E100's row names the scenario `order-503-once` but asks for "exact request/key reused for uncertain transport failure", and the uncertain transport failure is the network-error flavour. Scenario 1.3 therefore drives `offline-once-order`: the failure arrives as `data-error-code="UNKNOWN"`, and the screen does offer a retry for it — the failure notice carries no separate retry control, but the `review-submit` call to action stays enabled and its second press goes through — so `fail-once-order` was not needed. The 503 flavour's own failure screen is `specs/checkout-fault-paths.md` scenario 1.1.

Locator conventions, as in the sibling plans: controls built on the `app-button` primitive are host elements carrying the test id, so a press targets the native button inside them, `page.getByTestId('<id>').getByRole('button')`; prices come from the `app-price-block` primitive, whose digits sit in `price-amount` with the "Ft" glyph as a separate span beside them. The product page's call to action has two mounts: `add-to-cart-button` at 1024 px and wider, and the sticky rail's `purchase-cta` below 1024 px, where the side panel is hidden and the rail is the mount with a size; both carry the label "Kosárba teszem". Every other control a scenario names — the contact inputs and `contact-submit`, the cart controls, the delivery radios and `delivery-confirm`, the payment radios, the review cards, `review-consent-terms-input`, `review-submit`, the failure notices and the receipt — is present and visible at both widths, measured at 1920x1080 and at 390x844.

Numbers, each with its source. The mock's checkout store sets home delivery "Házhoz szállítás" at 1490 Ft and pickup "Átvételi pont" at 990 Ft below a 30 000 Ft subtotal and at 0 Ft from it (`DELIVERY_OPTIONS`, `FREE_SHIPPING_THRESHOLD_HUF`), a card payment at 0 Ft and cash on delivery "Utánvét" at 490 Ft (`PAYMENT_METHODS`), and it refuses cash on delivery above a 300 000 Ft cart (`CASH_ON_DELIVERY_MAX_CART_HUF`). Every other amount and count is what the screen showed in the run this plan was written from: the catalogue's first page reads "55 találat a szűrt feltételek szerint" with 12 `product-card` elements (it reads "Keresés a katalógusban…" while the first response is in flight), the first card that carries no `product-card-stock` marker is the 89 990 Ft one, and an order of it sums to Részösszeg 89 990 Ft, Szállítási díj 0 Ft, Fizetési díj 490 Ft and Végösszeg 90 480 Ft. That cart is above the free-shipping threshold, so both delivery options genuinely cost 0 Ft for it: the 0 Ft a scenario reads back after a retry is the server's own price and not the failure state's fabricated zero. The wizard normalizes the typed phone number, so the value typed as "+36 30 123 4567" is what the review page's summary shows as "+36301234567".

## Test Scenarios

### 1. Checkout: retry after one failure

**Seed:** `e2e/seed.spec.ts`

#### 1.1. [E068] the contact step saves on the second try and keeps what was typed

**File:** `e2e/integration/checkout-retry-contact-save-once.spec.ts`

**Steps:**

1. Open `/telefonok?mi-scenario=fail-once-checkout-update` and wait for `catalog-grid`. - expect: `result-count` reads "55 találat a szűrt feltételek szerint" and 12 `product-card` elements are rendered. - expect: `cart-badge` reads "0": a fresh context holds an empty cart under this scenario too.
2. Open the first `product-card` that carries no `product-card-stock` marker through its `product-card-cta`, then add the shown variant: at 1024 px and wider press the inner button of `add-to-cart-button` ("Kosárba teszem"); below 1024 px the side panel is hidden and the sticky rail's `purchase-cta` is the mount with a size, so press the inner button of `purchase-cta` ("Kosárba teszem") there. - expect: `product-page` is visible and `product-stock` reads "Raktáron a demó készletben". - expect: The confirmation ends with "1 darab a kosárban." and `cart-badge` reads "1".
3. Open the cart with the header's `cart-link` and press the inner button of `cart-continue` ("Tovább az adatokhoz"). - expect: `cart-page` shows exactly one `cart-line`. - expect: `contact-page` is visible on `/penztar/adatok` and its `h1` reads "Kapcsolattartási adatok".
4. Type "Teszt Elek" into `contact-fullname-input`, "teszt@example.test" into `contact-email-input` and "+36 30 123 4567" into `contact-phone-input`, then press the inner button of `contact-submit` ("Tovább a szállításhoz"). - expect: The browser stays on `/penztar/adatok`: the wizard does not advance and `delivery-step` is not rendered. - expect: `contact-save-error` is rendered and reads "A mentés sikertelen. Próbáld újra.". - expect: `contact-save-error` carries no control of its own — no "Bezárás" and no "Újrapróbálom" — so the retry this step offers is the same `contact-submit` button pressed again. - expect: Nothing was lost: `contact-fullname-input` holds "Teszt Elek", `contact-email-input` holds "teszt@example.test" and `contact-phone-input` holds "+36 30 123 4567". - expect: Each field's wrapper carries `data-state="server-error"`, and the inner button of `contact-submit` reads "Tovább a szállításhoz" and is enabled again.
5. Press the inner button of `contact-submit` a second time, changing nothing. - expect: The wizard advances: the URL is `/penztar/szallitas` and `delivery-step` is visible with the `h1` "Átvétel és fizetés". - expect: `contact-save-error` is gone, and the step renders its own controls: `delivery-options`, `payment-selector` and the summary `delivery-summary`. - expect: No `delivery-radio` and no `payment-radio` is checked, because the step preselects nothing.
6. Read what carries the typed values, since the delivery step shows no contact summary of its own: it renders no contact input and no contact summary element, so complete the step to reach the page that does. Choose "Házhoz szállítás" by its `delivery-radio`, fill "1052" into `address-input-postalCode`, "Budapest" into `address-input-city` and "Fő utca 1." into `address-input-line1` inside `address-form`, keep the "A számlázási cím megegyezik a szállítási címmel" tick, choose "Utánvét" by its `payment-radio` and press the inner button of `delivery-confirm` ("Tovább az ellenőrzéshez"). - expect: `review-page` is visible on `/penztar/ellenorzes`. - expect: The contact summary `review-contact` carries the typed values: it reads "Név Teszt Elek", "E-mail teszt@example.test" and "Telefon +36301234567" (the step's own normalization of "+36 30 123 4567"), so the second attempt's save is what the rest of the wizard is built on. - expect: `review-delivery` names "Házhoz szállítás" and `review-payment` reads "Utánvét".

#### 1.3. [E100] one order comes of a retried uncertain transport failure, with the same request and key

**File:** `e2e/integration/checkout-retry-order-once.spec.ts`

**Steps:**

1. Open `/telefonok?mi-scenario=offline-once-order` and wait for `catalog-grid`. - expect: `result-count` reads "55 találat a szűrt feltételek szerint" and 12 `product-card` elements are rendered. - expect: `cart-badge` reads "0": a fresh context holds an empty cart under this scenario too.
2. Open the first `product-card` that carries no `product-card-stock` marker through its `product-card-cta`, then add the shown variant: press the inner button of `add-to-cart-button` at 1024 px and wider, and of the sticky rail's `purchase-cta` below 1024 px, where the side panel is hidden. - expect: `product-page` is visible and `product-stock` reads "Raktáron a demó készletben". - expect: The confirmation ends with "1 darab a kosárban." and `cart-badge` reads "1".
3. Open the cart with `cart-link`, press the inner button of `cart-continue`, fill the contact step with "Teszt Elek", "teszt@example.test" and "+36 30 123 4567" and press the inner button of `contact-submit`; then on the delivery step choose "Házhoz szállítás" by its `delivery-radio`, fill "1052" / "Budapest" / "Fő utca 1.", keep the billing "same as delivery" tick, choose "Utánvét" by its `payment-radio` and press the inner button of `delivery-confirm`. - expect: `review-page` is visible on `/penztar/ellenorzes` and `review-page` carries `data-status="ready"`. - expect: `review-payment` reads "Utánvét", `review-items` lists exactly one `review-line` and `review-summary` reads Részösszeg 89 990 Ft, Szállítási díj 0 Ft, Fizetési díj 490 Ft and Végösszeg 90 480 Ft. - expect: No `review-submit-failure` is rendered and no order request has been sent yet.
4. Start recording the browser's request events: every request whose method is `POST` and whose URL ends in `/api/v1/orders`, with its headers. Tick `review-consent-terms-input` ("Elfogadom a demó rendelési feltételeit.") and press the inner button of `review-submit` ("Demórendelés véglegesítése"). - expect: The terms tick is checked and the inner button of `review-submit` is enabled before the press. - expect: The browser stays on `/penztar/ellenorzes` and `order-receipt` is not rendered. - expect: `review-submit-failure` is rendered, its `data-error-code` reads "UNKNOWN" — a transport failure, not a 503 — and its message reads "A kosarad és az adataid megmaradtak. Próbáld újra, vagy módosítsd a fizetési módot.", with a "Fizetési mód módosítása" control (`review-change-payment`) beside it. - expect: The step's own banner `review-state-banner` reads "A rendelés leadása nem sikerült.". - expect: The draft stays: `review-contact` still reads "Teszt Elek", "teszt@example.test" and "+36301234567", `review-delivery` still names "Házhoz szállítás" and "Utánvét", `review-items` still lists one `review-line` and `review-summary` is still rendered. - expect: The terms tick is still checked and the inner button of `review-submit` is enabled again while the failure notice holds no retry control of its own, so the retry the screen offers is this same call to action pressed again. - expect: Exactly one recorded request matches, a `POST` to `/api/v1/orders`, and that attempt fails.
5. Press the inner button of `review-submit` again, changing nothing. - expect: The order goes through: the browser lands on `/penztar/siker/<orderId>` with an order id in the path and `order-receipt` visible. - expect: `success-heading` reads "Elkészült a demórendelésed." and `receipt-order-number` reads "DEMO-000001", the first order number this fresh session issues. - expect: `receipt-row-payment` contains "Utánvét", `receipt-row-status` reads "Demó rendelés visszaigazolva", `receipt-lines` lists the ordered variant with its colour, storage and "1 db", and `receipt-totals` reads Részösszeg 89 990 Ft, Szállítási díj 0 Ft, Fizetési díj 490 Ft and Végösszeg 90 480 Ft. - expect: Exactly two recorded requests are `POST`s to `/api/v1/orders`, and both carry the same `Idempotency-Key` header and the same `If-Match` header: the retry repeats the exact request rather than composing a new one (measured on this run: one key on both, and `if-match: "6"` on both).
6. Check that exactly one order came of the pair, by what the screen can show: read the receipt once more, then open the cart again keeping the scenario with a page load of `/penztar/kosar?mi-scenario=offline-once-order`. - expect: The receipt reads `receipt-order-number` "DEMO-000001" — the session has issued exactly one order number, so the pair of attempts produced one order rather than two — and `order-receipt` and `receipt-line` are each rendered exactly once on the page. - expect: The cart page shows its empty state: the title "A kosarad még üres.", the message "Nézd meg a demókészülékeket, és válaszd ki a kedvenced." and the action "Telefonokat nézek", with zero `cart-line`, so the placed order consumed the cart and nothing is left queued. - expect: No second order exists anywhere the screen can show it: only the one order number and the one receipt are reachable. For the reader, the mechanism underneath is that `offline-once-order` short-circuits inside `faultResponse` before the order handler's store runs, so the failed attempt commits nothing, and the retry's replay of the same `Idempotency-Key` returns the one stored result.

#### 1.4. [E103] the receipt is read back on the retry and no new transaction is made

**File:** `e2e/integration/checkout-retry-receipt-read-once.spec.ts`

**Steps:**

1. Open `/telefonok?mi-scenario=fail-once-order-read` and wait for `catalog-grid`, then place a cash-on-delivery order without a fault of its own: open the first `product-card` that carries no `product-card-stock` marker through its `product-card-cta`, add the shown variant (the inner button of `add-to-cart-button` at 1024 px and wider, of the sticky rail's `purchase-cta` below 1024 px), open the cart with `cart-link`, press the inner button of `cart-continue`, fill the contact step with "Teszt Elek", "teszt@example.test" and "+36 30 123 4567" and press the inner button of `contact-submit`, then on the delivery step choose "Házhoz szállítás", fill "1052" / "Budapest" / "Fő utca 1.", choose "Utánvét" by its `payment-radio`, press the inner button of `delivery-confirm`, tick `review-consent-terms-input` and press the inner button of `review-submit`. - expect: The submission itself is not faulted: `order-read` is the endpoint this scenario breaks, and it is a `GET` the success page does not call, since the page renders from the submission's own response. - expect: The browser lands on `/penztar/siker/<orderId>` with an order id in the path, `order-receipt` is visible and `success-heading` reads "Elkészült a demórendelésed.". - expect: `receipt-row-payment` names "Utánvét" and `receipt-demo-badge` reads "DEMO".
2. Record the receipt's values and the address bar: `receipt-order-number`, `receipt-lines`, `receipt-totals`, `receipt-row-delivery`, `receipt-row-payment` and the order id in `/penztar/siker/<orderId>`. - expect: `receipt-lines` holds exactly one `receipt-line` with the ordered phone, its colour and storage, "1 db" and the line total. - expect: `receipt-totals` reads Részösszeg 89 990 Ft, Szállítási díj 0 Ft, Fizetési díj 490 Ft and Végösszeg 90 480 Ft. - expect: `receipt-row-delivery` reads "Házhoz szállítás" and `receipt-row-payment` reads "Utánvét". - expect: The receipt carries no PII: `order-receipt` contains neither the name "Teszt Elek" nor the street "Fő utca 1." the scenario typed, since the success screen renders no name, address or e-mail. - expect: `receipt-order-number` is not empty (the run this plan was written from showed "DEMO-000001"); note the number and the order id, because the next step reopens exactly that URL.
3. Start recording the browser's request events: every request whose URL contains `/api/v1/orders`. Then open the receipt again as a fresh page load inside the fault, keeping the scenario: navigate to `/penztar/siker/<the recorded orderId>?mi-scenario=fail-once-order-read`. - expect: `success-heading` reads "A betöltés nem sikerült" and `success-error` is visible. - expect: `success-error`'s title reads "A visszatöltés nem sikerült", its message reads "A rendelés visszatöltése sikertelen." and its single control reads "Visszatöltés újra". - expect: `order-receipt`, `receipt-order-number` and `success-actions` are not rendered: the page never invents a receipt it could not read. - expect: The browser stays on `/penztar/siker/<orderId>?mi-scenario=fail-once-order-read`.
4. Press "Visszatöltés újra". - expect: The retry recovers: `success-error` is gone, `success-heading` reads "Elkészült a demórendelésed." and `order-receipt` is visible again, with `success-actions` back and exactly one `receipt-line`. - expect: `receipt-order-number` reads the same number recorded in the second step, `receipt-lines` the same one line, `receipt-totals` the same Részösszeg, Szállítási díj, Fizetési díj and Végösszeg, `receipt-row-delivery` the same "Házhoz szállítás" and `receipt-row-payment` the same "Utánvét" — the same transaction read back from the server, not a new one. - expect: The browser stays on `/penztar/siker/<orderId>?mi-scenario=fail-once-order-read`.
5. Check that no new transaction came of the retry, from the requests recorded since the receipt's own page load. - expect: The only order requests recorded after the placement are `GET`s to `/api/v1/orders/<orderId>` — the failed read and the retry's read — with no `POST` among them, so the retry re-reads the stored receipt rather than re-posting an order. The sibling plan's permanent-fault version of this screen re-reads the same way. - expect: The page holds exactly one `order-receipt`, exactly one `receipt-line` and one `receipt-order-number`, so the retry restored the existing receipt and created nothing.
