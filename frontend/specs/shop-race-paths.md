# MiBolt shop request-race test plan

## Application Overview

MiBolt is a Hungarian demo storefront: an Angular application served from the Playwright base URL with the in-page MSW mock behind it (no backend, no database). Every test starts in a fresh browser context, so it starts signed in with an empty cart, and the mock keeps its cart in that context's `sessionStorage`.

This plan covers the three `race` rows of `docs/spec/test-scenarios.md`, all three driven through the mock's `?mi-scenario=slow-once-<operation>` family: it answers the first matching request of one page load 2000 ms late (`SLOW_ONCE_DELAY_MS` in the shop mock's `faults.ts`; the operations are `FAULT_OPERATIONS`) and every later one at once, so a newer request can overtake the held one. The mock reads the scenario when the document loads, remembers it for the tab and builds its handlers once per document, so each scenario opens its first page with the query; every page load of the scenario arms the fault again, a `page.goto` without the query included, while an in-app navigation keeps the fault but drops the query from the address.

(E037) — the row reads "Type first query then change before response" with "New results survive delayed old response; no double subscription." The held list request is the one the page load fires for its `?q=<word>`; the query is then changed inside the 2000 ms window through the search field the screen keeps usable while that request is in flight, the header's own: `header-search-input` at 1024 px and wider and `mobile-search-input` below it. The catalogue's own `filter-search-input` cannot serve here — it is mounted only in the 1024 px-and-wider sidebar and it is disabled with the panel's `aria-busy="true"` for the whole held window (measured), and the filter drawer below 1024 px carries no search field at all.

(E038) — the row reads "Switch between product routes rapidly" with "Old product cannot overwrite current slug or title." The held request is the first product's `GET /api/v1/products/<slug>`; while it is held the product page shows only its loading state and the header's "Mobiltelefonok" link, because a product page's related strip is requested only after the product itself has loaded — so there is no in-page link to another product to switch through, and the switch the scenario uses goes back through the catalogue with the browser's back.

(E039) — the row reads "Request quantity then another valid action" with "Dispatch uses fresh returned version; no lost update." This demo's cart has no quantity stepper and no quantity field anywhere, and while a cart write runs the add control is natively disabled for the whole held window (measured, in both mounts), so the second valid cart write the screen offers is the add control itself, pressed as soon as the screen accepts it again: the same variant's repeat add, which raises the line's quantity instead of creating a second line.

Two measured facts hold across all three. First, the app cancels the superseded request instead of letting a late answer land — Playwright reports it as a failed request whose failure text is the engine's own (`net::ERR_ABORTED` in Chromium, `NS_BINDING_ABORTED` in Firefox) and is not asserted — so each scenario pins that settlement and then keeps its check open across the moment the late answer would have arrived. Second, the product page swaps its purchase mount at 1024 px: `add-to-cart-button` at that width and wider, the `purchase-cta` inside `purchase-rail` below it; controls built on the `app-button` primitive are host elements carrying the test id, so a press targets the native `button` inside them.

No product slug and no product name is written into any scenario: every card is picked by what the screen shows, and each slug is read out of the address after the click. The counts and the Hungarian copy in the expectations are the ones measured on the running app.

## Test Scenarios

### 1. Shop: a newer request wins the race

**Seed:** `e2e/seed.spec.ts`

#### 1.1. [E037] a second search keeps its results when the first one answers late

**File:** `e2e/integration/shop-race-stale-search.spec.ts`

**Steps:**

1. Read the held window: open `/telefonok?q=motorola&mi-scenario=slow-once-products` (the first `products` request of this page load is the one the mock holds for 2000 ms) and read the catalogue. - expect: `result-count` reads "Keresés a katalógusban…". - expect: `catalog-loading` is visible and no `product-card` is rendered: the held first search's list has not arrived. - expect: At 1024 px and wider `filter-panel` carries `aria-busy="true"` and its `filter-search-input` is disabled, which is why the change in step 2 goes to the header's field; below 1024 px that panel is hidden and the search on screen is `mobile-search-input`. - expect: The address carries `q=motorola` and `mi-scenario=slow-once-products`.
2. Change the query inside the held window: fill the header's search field — `header-search-input` at 1024 px and wider, `mobile-search-input` below 1024 px — with `honor`, then commit it with Enter. - expect: The address carries `q=honor` and no longer carries `q=motorola`. - expect: `result-count` reads "8 találat a szűrt feltételek szerint". - expect: Eight `product-card` elements are rendered, and no card's text contains the first word (`motorola`, any case). - expect: `applied-chip` reads "Keresés: „honor” ✕".
3. Hold the check across the moment the first search's answer would have landed (2000 ms after its own request): settle the superseded request, then keep reading the grid. - expect: The superseded request is never answered: the page reports the `products` request carrying `q=motorola` as a failed request — the app cancels it; the failure text is engine-specific and is not asserted — and no `products` response carries `q=motorola`. The check is an `expect.poll` over the flag the spec captured from `page.on('requestfailed')` before the navigation, inside the 5 s expect timeout. - expect: Exactly one `products` request carries `q=honor`: the change issued one request and no second subscription. - expect: The newer result survives the late window: sampling the counter and the grid with `expect.poll` at two samples about 2.5 s apart (timeout 5 s) reads "8 találat a szűrt feltételek szerint" and eight `product-card`s at both samples, and no sample shows a card carrying the first word. - expect: The address still carries `q=honor`.

#### 1.2. [E038] a second product page keeps its address and heading when the first product answers late

**File:** `e2e/integration/shop-race-stale-product.spec.ts`

**Steps:**

1. Open `/telefonok?mi-scenario=slow-once-product`, wait for the grid, and read the first two cards. - expect: `result-count` reads "55 találat a szűrt feltételek szerint" and twelve `product-card` elements are rendered. - expect: Each of the first two cards' `product-card-cta` carries a `?variant=` link; both cards' names, shown colours and storage sizes are read from the cards themselves, and neither card carries a `product-card-stock` marker.
2. Open the first card through its `product-card-cta`, read its slug out of the address and note it as the first slug, then read the page while the product's request is held. - expect: The address is `/telefonok/<first slug>?variant=<the first card's variant>` and the first slug is the one read here, not a literal. - expect: `product-page` is visible with `product-loading`, because the request `GET /api/v1/products/<first slug>` is the one the mock holds for 2000 ms. - expect: `product-name` is not rendered and `related-products` is not on screen: the strip is requested only after the product has loaded, so the only `/telefonok` link on screen is the header's "Mobiltelefonok" (`/telefonok`) — there is no in-page link to another product to switch through.
3. Switch routes before the held answer lands: go back to the catalogue with the browser's back, wait for the grid, and open the second `product-card` through its `product-card-cta`. - expect: The address becomes `/telefonok/<second slug>?variant=<the second card's variant>`, and the second slug differs from the first. - expect: `product-name` renders the second card's name read in step 1. - expect: The switch happened inside the held window: the page reports `GET /api/v1/products/<first slug>` as a failed request when the second product page requests its own, so the first product's request is cancelled rather than answered.
4. Hold the check across the moment the first product's answer would have landed and re-read the page. - expect: `product-loading` is hidden: the second product page has finished loading. - expect: `product-name` still names the second card's phone, and the page never shows the first card's name. - expect: The address still carries the second slug and its `?variant=`. - expect: `document.title` still reads "MiBolt — Termék": the product route's own title carries no product name (measured on the running app), so the heading `product-name` is what a stale write would change. - expect: Sampling `product-name` and the address with `expect.poll` at two samples about 2.5 s apart (timeout 5 s) shows the second phone and the second slug at both samples.

#### 1.3. [E039] a second add keeps the cart's fresh version when the first add answers late

**File:** `e2e/integration/shop-race-stale-cart-write.spec.ts`

**Steps:**

1. Open `/telefonok?mi-scenario=slow-once-cart-add`, wait for the grid, and open the first `product-card` with no `product-card-stock` marker through its `product-card-cta`. - expect: `product-page` is visible, `product-stock` reads "Raktáron a demó készletben", and `cart-badge` reads "0": a fresh context holds an empty cart. - expect: The "Készülékár" block shows an amount in `price-amount` and the selected colour and storage are read from `variant-color-group` and `variant-storage-group` (on the first card, measured: "Zöld", "256 GB", 89 990 Ft). - expect: The add control the viewport shows is enabled: the inner button of `add-to-cart-button` at 1024 px and wider, the inner button of `purchase-cta` inside `purchase-rail` below 1024 px.
2. Press that add control — this is the write the mock holds for 2000 ms — and read the screen while it is in flight. - expect: The control is disabled for the whole held window, and the mount says so: at 1024 px and wider `add-to-cart-button` is disabled with `add-to-cart` at `aria-busy="true"` and its status reads "A termék hozzáadása a kosárhoz…"; below 1024 px the rail's `purchase-cta` is disabled and carries the loading label "Hozzáadás…". - expect: `cart-badge` still reads "0": the held write has not landed. - expect: The variant selector stays usable (`variant-color-*` and `variant-storage-*` are enabled), but no control on this screen writes to the cart while the add runs, and the cart has no quantity stepper or quantity field anywhere — so the row's "Request quantity then another valid action" is taken as the screen offers it: the next valid cart write is this same add control.
3. Wait for the held write to land, reading it from the mount's own status. - expect: The confirmation reads "<phone name>, <colour>, <storage> – 1 darab a kosárban.", beside its "Bezárás" dismiss control. - expect: `cart-badge` reads "1". - expect: The add control is enabled again: the screen now accepts the second valid cart write.
4. Press the same add control again, without changing the selected colour or storage. - expect: The confirmation reads "<phone name>, <colour>, <storage> – 2 darab a kosárban.": the second dispatch was accepted on top of the first, so it carried the version the first write returned, where a stale `If-Match` would have been refused instead. - expect: `cart-badge` reads "2". - expect: No error copy and no conflict copy is shown in the mount: the confirmation was replaced by another confirmation, not by a refusal.
5. Open the cart with the header's `cart-link` and read it. - expect: `cart-page` is visible (the checkout layout's header carries no `cart-badge`, so the badge was read in step 4). - expect: Exactly one `cart-line` is rendered and it carries both writes: `cart-line-name` is the phone's name read in step 1, `cart-line-quantity` reads "2 db", and its `price-amount` reads 179 980 — twice the unit price read in step 1 (89 990). - expect: `cart-count` reads "Kosárban található termékek (1)": the repeat add merged into the line instead of adding a second one. - expect: The totals match the lines: `order-summary-subtotal` names "Részösszeg" with 179 980 in its `price-amount`, the line's own amount, while `order-summary-total` still reads "Végösszeg" with the "Nincs megjeleníthető ár." placeholder and no `price-amount`, because the shipping fee is chosen on the delivery step. - expect: No `cart-notice` and no error copy is rendered on the cart page: neither write was refused and no conflict was surfaced.
