# MiBolt storage story paths test plan

## Application Overview

MiBolt is a Hungarian demo storefront: an Angular application served from the Playwright base URL with the in-page MSW mock behind it (no backend, no database), and the demo access gate starts signed in on the default scenario, so one fresh browser context is an empty cart with no sign-in step. These five scenarios come from `docs/spec/test-scenarios.md` (rows E013, E014, E015, E017 and E059) and every one of them starts from a fresh page and can run in any order.

The mock keeps its state in the browsing context's `sessionStorage` under the key `mi-bolt.snapshot.default`, a JSON document whose `schemaVersion` is 4 (`Persistence`/`SNAPSHOT_SCHEMA_VERSION` in `projects/shop-mocks/src/persistence.ts`), and the tab-scoped demo session id lives under `mi-bolt.demo-session`. On boot `Persistence.hydrate` reads that entry and, when it is not JSON, fails the shape allowlist, carries another `schemaVersion`, or was saved more than seven days ago, it removes the entry and returns nothing: the shop then starts with an empty cart and no message at all. The seeded cart carries its own `expiresAt`, and a cart that has passed it answers `410 CART_EXPIRED` on the next read (`CartStore`/`ensureFreshCart` in `projects/shop-mocks/src/cart/cart-store.ts`), the mock forgets it, and the read after that creates a fresh empty cart.

Three screens carry the states these rows are about. The demo strip `demo-notice` renders `demo-notice-memory-text` reading "A böngésződ nem engedi a mentést, ezért az oldal frissítésekor a kosarad tartalma elveszik." when the mock's bootstrap found browser storage denied (`DemoNotice`, `AppShell` and `PERSISTENCE_MODE`, fed by `startMocks` in `projects/storefront/src/core/bootstrap-demo.ts`); the ordinary strip reads "Fiktív termékek és árak. A vásárlás szimulált; nem történik valódi fizetés.". The fatal startup surface is the `#mi-bolt-fatal` template in `projects/storefront/src/index.html`, cloned into the page by `showFatal` in `projects/storefront/src/main.ts` when `startMocks()` rejects: the title "A MiBolt demó indítása sikertelen", the body "A bemutató nem tudott elindulni. Frissítsd az oldalt, vagy ellenőrizd a böngésző konzolját a részletekért." and the button `fatal-retry` "Újratöltés", which reloads the page.

Products are never named by slug or product name: every scenario picks its phone by what the screen shows (the first card carrying no `product-card-stock` marker, whose stock line then reads "Raktáron a demó készletben"), and reads the variant id out of the address bar or a card's detail link only where a later step needs it. The product page mounts its purchase call to action twice: the inner button of `add-to-cart-button` is the one at 1024 px and wider, and the sticky rail's `purchase-cta` is the one below 1024 px, where the side panel's control is in the DOM but not visible. Controls built on the `app-button` primitive are host elements carrying the test id, so a press targets the native `button` inside them.

For E017 the planning browser settled which way of stopping the mock's worker gives the fatal surface. A context from `browser.newContext({ serviceWorkers: 'block' })` does: the page shows "A MiBolt demó indítása sikertelen" with the retry button, `app-root` stays empty, and not one request to `/api/v1/` leaves the page. Aborting `mockServiceWorker.js` with `page.route` did not: in the planning page's context the worker was already registered, so the script was never re-fetched, the shop booted normally, and the call did not return. A blocked context cannot be un-blocked, so the retry cannot recover inside it; the scenario therefore checks the fatal surface in that context and then arms the same failure once, in the test's own page, with `page.addInitScript` replacing `navigator.serviceWorker.register` for the first page load only, which is the construction the retry step needs and which was measured to work end to end.

Three rows ask for something the screens do not offer today. E013 and E014 ask for the reset to be explained (issue MIM-448) and E059 for the expiry to be stated (issue MIM-449). Those three scenarios end with a `**Not yet in the application:**` line naming the missing expectation, the issue and what the screen does instead; no control or message is invented for them, and no step in this plan names one.

## Test Scenarios

### 1. Shop: storage, startup and expired-cart stories

**Seed:** `e2e/seed.spec.ts`

#### 1.1. [E013] a corrupt saved state is dropped and the shop still works

**File:** `e2e/integration/storage-story-corrupt-snapshot.spec.ts`

**Steps:**

1. Before the first navigation, install the corrupt entry and start the listeners. `page.addInitScript` writes the truncated JSON document `{"schemaVersion":4,"providerId":"mi-bolt",` under `mi-bolt.snapshot.default` in `window.sessionStorage`, but only when its own marker key `mi-bolt.story-seeded` is absent, and then sets that marker, so only the first page load of the scenario carries the corrupt entry and every later load boots from what the app itself saved. Register `page.on('pageerror', …)` and record every `console` message. Then open `/` with an explicit timeout (`page.goto('/', { timeout: 10000 })`) and wait for `hero-heading`. - expect: The home page renders instead of falling over: `hero-heading` is visible and the `h1` reads "A következő mobilod. Egyszerűen.". - expect: `cart-badge` in the header reads "0": the shop started with an empty cart. - expect: `demo-notice` reads "DEMÓ" followed by "Fiktív termékek és árak. A vásárlás szimulált; nem történik valódi fizetés." — the ordinary demo strip, not the memory variant. - expect: No `app-status-message` element is rendered and no `cart-notice` appears anywhere on the page: nothing on screen mentions the saved state that was thrown away. - expect: `sessionStorage.getItem('mi-bolt.snapshot.default')` is `null`: the corrupt entry was removed at boot, starting with an empty cart and no message. - expect: The recorded page errors are empty: no `pageerror` fired, and the console holds no error and no warning.
2. Open the catalogue with an explicit timeout (`page.goto('/telefonok', { timeout: 10000 })`), wait for `catalog-grid`, and count the `product-card` elements and read `cart-badge`. - expect: `catalog-grid` is rendered with 12 `product-card` elements: browsing works on the dropped state. - expect: `cart-badge` still reads "0".
3. Open the first `product-card` that carries no `product-card-stock` marker, through its `product-card-cta`, read `product-name`, and add it: press the inner button of `add-to-cart-button` at 1024 px and wider, or the sticky rail's `purchase-cta` below 1024 px, where the side panel's control is hidden. - expect: `product-page` is visible and `product-stock` reads "Raktáron a demó készletben", because the card was picked for carrying no "Elfogyott" marker. - expect: The press lands: `cart-badge` in the header reads "1".
4. Open the cart with the header's `cart-link`, read it, and then read `sessionStorage.getItem('mi-bolt.snapshot.default')` with a page script. - expect: `cart-page` is visible with exactly one `cart-line`, whose `cart-line-name` is the name read from `product-name` and whose `cart-line-quantity` reads "1 db". - expect: The stored entry is valid JSON again, carries `schemaVersion` 4 and holds exactly that one line in `cart.items`: the shop saved a fresh snapshot in place of the corrupt one. - expect: No `pageerror` fired during the whole scenario.
5. **Not yet in the application:** "Explain reset" — the corrupted entry is dropped without a word: no screen carries any message about the discarded saved state (issue MIM-448), and the shop shows its ordinary demo strip and an empty cart instead.

#### 1.2. [E014] an older snapshot version is discarded and its line stays hidden

**File:** `e2e/integration/storage-story-old-schema.spec.ts`

**Steps:**

1. Read the shop's own snapshot first. Open `/telefonok` (explicit timeout), wait for `catalog-grid`, read the `?variant=` value out of the detail link of a second `product-card` that carries no `product-card-stock` marker (its `product-card-cta` href) — the line the older entry will carry — then open the first in-stock card through its `product-card-cta`, read `product-name`, add it (inner button of `add-to-cart-button` at 1024 px and wider, `purchase-cta` below 1024 px), and read `sessionStorage.getItem('mi-bolt.snapshot.default')` with a page script. - expect: `cart-badge` reads "1". - expect: The entry parses as JSON with `schemaVersion` 4, `providerId` "mi-bolt", `savedAt`, `expiresAt`, and a `cart` object holding `id`, `version`, `createdAt`, `expiresAt` and `items`. - expect: The second card's variant id differs from the one now in the cart, so the hidden line is a different line from the one the scenario adds.
2. Build the older entry from what was read — the same document with `schemaVersion` 3 and `cart.items` replaced by one line holding the second card's variant id with `quantity` 1; the top-level `savedAt` and `expiresAt` stay in the future, so the age check is not what rejects it — and install it with `page.addInitScript` before the next `page.goto`, guarded by the marker key `mi-bolt.story-seeded` so it is planted once. Register `page.on('pageerror', …)`, then open `/` with an explicit timeout and wait for `hero-heading`. - expect: The shop boots: `hero-heading` is visible. - expect: `cart-badge` reads "0": the line the older entry carries is not restored. - expect: `sessionStorage.getItem('mi-bolt.snapshot.default')` is `null`: the incompatible entry was removed at boot. - expect: No `app-status-message` is rendered: nothing says a saved state of an older version was discarded. - expect: No `pageerror` fired.
3. Open `/telefonok` (explicit timeout), wait for `catalog-grid` (12 `product-card` elements), open the first in-stock card, read `product-name`, add it as in the previous scenario, then open the cart with the header's `cart-link`. - expect: `cart-badge` reads "1" and `cart-page` holds exactly one `cart-line`, whose `cart-line-name` is the phone read from `product-name`. - expect: No `cart-line` names the variant the older entry carried: the hidden line did not come back, although that variant exists in the catalogue and would render if the version check let it through. - expect: `cart-count` reads "Kosárban található termékek (1)".
4. Reload with `page.goto(page.url(), { timeout: 10000 })` and read the cart again. - expect: Exactly one `cart-line` is rendered and its `cart-line-name` is still the phone added in the previous step: the older entry was not replayed and no false order line appeared. - expect: `sessionStorage.getItem('mi-bolt.snapshot.default')` parses, carries `schemaVersion` 4 and holds only that one line. - expect: No `pageerror` fired during the whole scenario.
5. **Not yet in the application:** "Discard incompatible data under explicit version policy" — the version policy is silent: no screen states that a saved state of an older version was discarded (issue MIM-448), and the shop starts with an empty cart and its ordinary demo strip instead.

#### 1.3. [E015] blocked storage keeps shopping in memory and announces the reload limitation

**File:** `e2e/integration/storage-story-memory-mode.spec.ts`

**Steps:**

1. Before the first navigation, install the storage denial: `page.addInitScript` redefines `sessionStorage` on `window` with `Object.defineProperty(window, 'sessionStorage', { configurable: true, get() { throw new DOMException('The operation is insecure.', 'SecurityError'); } })`, which is what a browser that blocks site data does. Record every `console` message, then open `/` with an explicit timeout and wait for `hero-heading`. - expect: `demo-notice` renders `demo-notice-memory-text` reading exactly "A böngésződ nem engedi a mentést, ezért az oldal frissítésekor a kosarad tartalma elveszik.". - expect: The strip reads "DEMÓ" and then that sentence, and `demo-notice` carries the `demo-notice--memory` class; the ordinary "Fiktív termékek és árak. A vásárlás szimulált; nem történik valódi fizetés." sentence is not rendered. - expect: `cart-badge` reads "0". - expect: The console carries the warning "[mi-bolt] persistence: sessionStorage denied, using in-memory cache; reload will not restore snapshot.".
2. Open `/telefonok` (explicit timeout), wait for `catalog-grid` (12 cards), open the first in-stock card through its `product-card-cta`, read `product-name`, and add it: the inner button of `add-to-cart-button` at 1024 px and wider, the sticky rail's `purchase-cta` below 1024 px. - expect: `product-stock` reads "Raktáron a demó készletben" and the press lands: `cart-badge` reads "1". - expect: The add works although nothing can be written to storage: the shop is running from memory.
3. Open the cart with the header's `cart-link` and read it. - expect: `cart-page` is visible with exactly one `cart-line`, its `cart-line-name` the name read from `product-name` and its `cart-line-quantity` "1 db". - expect: `demo-notice-memory-text` is still rendered on the cart page, above the line.
4. Reload with `page.goto(page.url(), { timeout: 10000 })` and read the cart page again. - expect: No `cart-line` is rendered, and `empty-state` is shown with the title "A kosarad még üres.", the message "Nézd meg a demókészülékeket, és válaszd ki a kedvenced." and the action "Telefonokat nézek". - expect: `cart-count`, `order-summary` and `cart-continue` are gone with the line. - expect: `demo-notice-memory-text` still reads the memory sentence: the limitation the page announced is what the reload then did. - expect: No `pageerror` fired.

#### 1.4. [E017] a demo that cannot start its mock shows the retryable fatal screen

**File:** `e2e/integration/storage-story-worker-fails.spec.ts`

**Steps:**

1. Open the demo in a context whose service workers are blocked: `browser.newContext({ serviceWorkers: 'block', baseURL: testInfo.project.use.baseURL, viewport: testInfo.project.use.viewport })`, open a page in it, record every request to `**/api/v1/**` and every `console` message, and open `/` with an explicit timeout (`page.goto('/', { timeout: 10000 })`). - expect: The fatal startup surface is shown instead of the shop: the title reads "A MiBolt demó indítása sikertelen" and the body reads "A bemutató nem tudott elindulni. Frissítsd az oldalt, vagy ellenőrizd a böngésző konzolját a részletekért.". - expect: `fatal-retry` is rendered as a native `button` reading "Újratöltés". - expect: No screen of the application is rendered: `hero-heading` is absent, `app-root` holds no children, and the `#mi-bolt-splash` cover screen is gone. - expect: Not one request to `/api/v1/` leaves the page, so no business call can answer with data and nothing falls through to the network. - expect: The console carries the warning "Service Worker registration blocked by Playwright" and the error "[MiBolt] Bootstrap failed: Error", which is the mock's own start failing; Chromium and WebKit append the error's message to that prefix, while Firefox prints the error's name alone, so the spec asserts only the prefix every engine prints.
2. Close that context. In the test's own page arm the same failure once, before the next navigation: `page.addInitScript` checks its marker key `mi-bolt.story-worker-blocked-once`, and when the marker is absent it stores the marker and replaces `navigator.serviceWorker.register` with a function returning `Promise.reject(new Error('worker blocked for the story'))`. Record every request to `**/api/v1/**`, open `/` with an explicit timeout, and wait for the fatal surface. - expect: The same fatal surface is shown: the title "A MiBolt demó indítása sikertelen", the same body sentence, and `fatal-retry` reading "Újratöltés". - expect: `hero-heading` is absent and `app-root` holds no children: the demo did not half-start behind the failure. - expect: Not one request to `/api/v1/` leaves the page, so no business API answers with data.
3. Press `fatal-retry` and wait for the page load it starts to settle (`page.waitForFunction` for `hero-heading` or the fatal title, explicit `{ timeout: 6000 }`). - expect: The retry loads the shop: `hero-heading` is visible and the fatal surface is gone. - expect: The shop is working again: `cart-badge` reads "0" and the URL is `/`. - expect: The marker key `mi-bolt.story-worker-blocked-once` is still in `sessionStorage`, so the failure was armed for the first page load only and the reload is the whole of what the retry needed.

#### 1.5. [E059] an expired cart becomes a fresh empty one and cannot be ordered from

**File:** `e2e/integration/storage-story-expired-cart.spec.ts`

**Steps:**

1. Read what the shop's own snapshot looks like. Open `/telefonok` (explicit timeout), wait for `catalog-grid`, open the first in-stock card, read `product-name`, add it (inner button of `add-to-cart-button` at 1024 px and wider, `purchase-cta` below 1024 px), then read `sessionStorage.getItem('mi-bolt.snapshot.default')` and `sessionStorage.getItem('mi-bolt.demo-session')` with a page script. - expect: `cart-badge` reads "1". - expect: The entry parses as JSON with `schemaVersion` 4, `providerId` "mi-bolt", a `simulatedSessionId` equal to the demo session id, top-level `savedAt` and `expiresAt`, and a `cart` with `id`, `version`, `createdAt`, `expiresAt` and one `items` line holding the added variant id with `quantity` 1.
2. Build the expired entry from it: keep everything and move `cart.createdAt` two days back and `cart.expiresAt` one day back, so `cart.expiresAt` is after `cart.createdAt` and both are before now, while `savedAt` and the top-level `expiresAt` stay where they are so the snapshot itself is not stale. Install it with `page.addInitScript` before the next `page.goto`, writing both `mi-bolt.snapshot.default` and `mi-bolt.demo-session` (the mock finds the seeded cart by the session id), and record every `console` message. The mock's responses are produced inside the service worker, so the expired read is observed through that console record: the line the mock writes for the read, which every engine prints. The read's 410 also reaches `page.on('response')` in Chromium, Firefox and WebKit, so the spec asserts the console line for its identical content across engines, not because response events miss the read. - expect: The installed cart's `expiresAt` lies before the current time, which is the state the row's "Restore expired cart" means.
3. Open `/penztar/kosar` with an explicit timeout and wait until `cart-page` has left its loading state, then read the page. - expect: The first read of the cart answers 410 Gone. The spec reads it through the mock's own console line for that read (`[MSW] <time> GET /api/v1/cart (…410 Gone`), which every engine prints, and the 410 also reaches `page.on('response')` in Chromium, Firefox and WebKit. The browser's own "Failed to load resource: the server responded with a status of 410 (Gone)" line, which Chromium and WebKit log, is never printed by Firefox. - expect: The page settles on the empty state rather than on an error: exactly one `empty-state` is rendered, reading "A kosarad még üres.", "Nézd meg a demókészülékeket, és válaszd ki a kedvenced." and the action "Telefonokat nézek" — the shop reads the cart again and a fresh empty cart answers. - expect: No `cart-line`, no `error-state`, no `cart-count`, no `cart-continue` and no `order-summary` is rendered. - expect: No `app-status-message` and no `cart-notice` is rendered: the screen says nothing at all about the expiry.
4. Deep-link the last step of the wizard: `page.goto('/penztar/ellenorzes', { timeout: 10000 })` and wait until the address changes or `review-page` appears. - expect: `review-page` is never rendered and the browser is on `/penztar/kosar?navigationReason=empty-cart` with `cart-page` visible: the expired cart cannot reach the order step, so no silent order can be placed on it. - expect: `navigation-reason` reads "A kosarad üres, ezért ide irányítottunk." with its "Bezárás" control. - expect: `review-submit` is absent from the page.
5. Press the empty state's "Telefonokat nézek" action. - expect: The catalogue is shown: the `h1` reads "Mobiltelefonok" and `product-card` elements are rendered. - expect: `cart-badge` reads "0": the shopper continues on the fresh empty cart the expired one was replaced by.
6. **Not yet in the application:** "Explicit expiry" — the expired cart is replaced without a word: the cart page and the review step's banner say only that the cart is empty, and nothing tells the shopper their cart expired rather than that it was emptied (issue MIM-449).
