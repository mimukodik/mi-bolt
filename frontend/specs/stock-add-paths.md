# MiBolt stock-add-path test plan

## Application Overview

MiBolt is a Hungarian demo storefront (Angular, served from the Playwright base URL) whose backend is mocked in the page by MSW: no server, no database. The buyer's path is the home page `/`, the phone list `/telefonok`, a product page `/telefonok/<slug>` and the cart `/penztar/kosar`; the demo gate starts signed in on the default scenario, and the mock keeps the cart in the browsing context's `sessionStorage`, so one fresh context IS an empty cart with no sign-in step.

`?mi-scenario=stock-lost-once-cart-add` is read from the query when the page loads and is held by the mock's handlers for the rest of the browsing context, in-app navigation included. Under it, the first add-to-cart request of that page load calls `stockLostOnce` before the cart store runs and takes the requested variant's whole demo stock, so the add is refused with a 409 `OUT_OF_STOCK` Problem while every later catalogue, product, cart and checkout read sees that variant as sold out. A `page.goto` without the query loads the default scenario with a cart of its own, so this scenario opens its first page with the query and moves on by clicking; no later step may navigate again.

The product page splits its buy chrome at 1024 px. At 1024 px and wider the in-flow `.cta-desktop` block is the visible one, carrying the add control's `add-to-cart-button` and the `add-to-cart-reason` hint, and the sticky `purchase-rail` is `display: none`; below 1024 px the rail is the visible one, carrying the `purchase-cta` button and the `purchase-rail-reason` paragraph. Both mounts stay in the DOM at both widths and both read the page's single add state, so the refusal banner is rendered twice and every assertion is scoped to the mount the viewport paints.

The refusal copy is the `OUT_OF_STOCK` line of the product page's `describeAddFailure`, and on that outcome the page re-reads the product (`refreshProduct`) so the stock line, the add control and the reason hint follow the changed stock, while the shopper's chosen colour and storage are left exactly as they were.

Products are never named by slug or product name anywhere in this plan: the scenario picks its card by what the screen shows (the first card that carries no `product-card-stock` marker and shows a colour swatch row) and reaches the product page by clicking that card's `product-card-cta`.

## Test Scenarios

### 1. Adding a phone that sells out meanwhile

**Seed:** `e2e/seed.spec.ts`

#### 1.1. [E060] a variant that sells out while it is being added is refused, stays selected and is shown as sold out

**File:** `e2e/integration/shop-edge-sold-out-while-adding.spec.ts`

**Steps:**

1. Open the catalogue with the stock-lost scenario on the URL's first load: `/telefonok` with `?mi-scenario=stock-lost-once-cart-add`, and wait for the grid. - expect: `result-count` reads "<n> találat a szűrt feltételek szerint" with n greater than 0 (the observed run's grid held 12 `product-card` elements), and at least one `product-card` is rendered. - expect: `cart-badge` in the shop header reads "0": a fresh browsing context holds an empty cart. - expect: No `error-state` and no `status-message` is on screen: the scenario arms the first add-to-cart request only and breaks no read.
2. Click the `product-card-cta` of the first `product-card` that carries no `product-card-stock` marker and shows a colour swatch row (`product-card-swatches` with two or more `product-card-swatch` buttons). - expect: `product-page` is visible, `product-name` is not empty, the "Készülékár" price block shows an amount, and `product-stock` reads exactly "Raktáron a demó készletben". - expect: The address bar moves to that card's own product page (`/telefonok/<slug>?variant=<id>`): the in-app navigation drops `mi-scenario` from the URL while the mock keeps the scenario for this browsing context. - expect: `variant-color-group` and `variant-storage-group` are both visible, so the product offers a colour and a storage to choose. - expect: `cart-badge` still reads "0".
3. Choose a colour and a storage: click the first enabled `variant-color-*` button whose `aria-pressed` is `false` (on the screen the observed run rendered, the button labelled "Ezüst"), then the first enabled `variant-storage-*` button whose `aria-pressed` is `false` (the button labelled "512 GB"). - expect: The clicked colour button has `aria-pressed="true"` and `aria-label` "<colour>, kiválasztva" ("Ezüst, kiválasztva" in the observed run), and every other colour button reads "<colour>, elérhető". - expect: The clicked storage button has `aria-pressed="true"` and `aria-label` "<storage>, kiválasztva" ("512 GB, kiválasztva"), and every other storage button reads "<storage>, elérhető". - expect: The page names the choice: `variant-color-group`'s legend reads "Szín: <colour>" ("Szín: Ezüst") and `variant-storage-group`'s legend reads "Tárhely: <storage>" ("Tárhely: 512 GB"). - expect: `product-stock` still reads exactly "Raktáron a demó készletben", the visible add control is enabled and reads "Kosárba teszem", and neither reason hint (`add-to-cart-reason`, `purchase-rail-reason`) is shown. - expect: The "Készülékár" amount is the chosen variant's price (708 990 in the observed run) and `cart-badge` still reads "0".
4. Press the visible add control: the inner button of `add-to-cart-button` at 1024 px and wider, the `purchase-cta` button inside `purchase-rail` below 1024 px. Under the scenario this is the page load's first add-to-cart request, so the mock takes the requested variant's whole demo stock and refuses the add with a 409 `OUT_OF_STOCK`. - expect: The visible `status-message` — the copy inside `add-to-cart` at 1024 px and wider, inside `purchase-rail` below — has role `alert` and severity error, and reads exactly "Ez a változat közben elfogyott, ezért nem került a kosárba.", with a "Bezárás" button; the other mount's copy stays painted out. - expect: The message names no 409, no Problem code and no server text: the shopper only learns the chosen variant has just sold out. - expect: No success message appears anywhere: the confirmation the page would otherwise show reads "<product name>, <colour>, <storage> GB – 1 darab a kosárban.", and it is never rendered. - expect: No cart drawer or mini-cart opens, because the app has none: the add reveals the refusal banner and nothing else.
5. Read the chosen variant and the availability the page now shows, without leaving the product page. - expect: The choice is still on screen, unchanged: the colour button keeps `aria-pressed="true"` and `aria-label` "<colour>, kiválasztva", the storage button keeps `aria-pressed="true"` and `aria-label` "<storage>, kiválasztva", and the legends still read "Szín: <colour>" and "Tárhely: <storage>". - expect: The address bar is unchanged, still the same product route with the chosen variant query (`/telefonok/<slug>?variant=<id>`): the refusal moved the shopper nowhere and reset no choice. - expect: `product-stock` now reads exactly "Ez a konfiguráció elfogyott a demó készletből.", because the page re-read the product after the refusal and the availability line follows the changed stock. - expect: The visible add control is now disabled and still reads "Kosárba teszem". - expect: The visible reason hint — `add-to-cart-reason` at 1024 px and wider, `purchase-rail-reason` below — reads exactly "Ez a változat jelenleg nem elérhető." - expect: `cart-badge` still reads "0" and no `error-state` appears on the product page: the refused add changed nothing.
6. Click the header's `cart-link` to open the cart. - expect: The address bar becomes `/penztar/kosar` and `cart-page` is rendered. - expect: Zero `cart-line` is rendered, so the cart holds no line of that product: the refused add left the cart exactly as it was. - expect: The cart shows its empty state: the heading "A kosarad még üres.", the message "Nézd meg a demókészülékeket, és válaszd ki a kedvenced." and the action "Telefonokat nézek". - expect: The chosen product's name is nowhere on the cart page, and the refusal banner does not follow the shopper here.
