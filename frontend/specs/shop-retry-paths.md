# MiBolt shop retry test plan

## Application Overview

MiBolt is a Hungarian demo storefront: an Angular application served from the Playwright base URL with the whole backend mocked in the page by MSW (no server, no database). The demo access gate starts signed in, so one fresh browser context needs no sign-in step, and the mock keeps its state (cart, checkout draft, payment intents, receipts) in that context's `sessionStorage` under `mi-bolt.snapshot.<scenario>`. The scenario name therefore namespaces the stored cart: two page loads that carry the same `?mi-scenario=` value share one cart, while a load with a different value, or none, starts a cart of its own.

The four scenarios drive the once-only fault family of rule 12 of `e2e/seed.spec.ts`. `?mi-scenario=fail-once-<operation>` answers the first matching request of each page load with a 503 and serves every later one, so the screen's own retry recovers; the operations are the ones `FAULT_OPERATIONS` lists in `projects/shop-mocks/src/faults.ts`. "Once" is once per handler list, and the browser builds one list per page load: a `page.goto` that keeps the query arms the fault again, while in-app navigation and a retry inside the page do not. Every scenario opens its first page with the query and keeps it on every `page.goto`; an in-app link may drop the query from the address bar, and the fault survives that.

Two facts govern what a failure looks like on screen. No server message ever reaches the page, so each screen prints its own Hungarian copy with a general "Ismeretlen hiba …" line; and every failure renders the shared error state (`error-state`, role `alert`, or role `status` on the home page) built from the screen's own title, message, optional hint and retry button. Only the home page's featured retry carries a test id of its own (`retry-button`); the catalogue's and the product page's error states carry only `error-state`, so their retry is named as that state's own button with the text "Újrapróbálom".

Products are never named by slug or product name: every scenario picks its phone by what the screen shows (the first card with no `product-card-stock` "Elfogyott" marker) and reads the slug from the address bar only where a later step needs it. Controls built on the `app-button` primitive are host elements carrying a test id, so a press targets the native `button` inside them: `page.getByTestId('<id>').getByRole('button')`. Prices come from the `app-price-block` primitive, whose digits sit in `price-amount` with the `Ft` glyph as a separate span beside them. Every step that names a control which differs by width names both mounts: the catalogue's filters are the sidebar (`filter-*`) at 1024 px and wider and the drawer opened by `filter-trigger` (`drawer-*`, applied with `drawer-apply`) below it, and the product page's call to action is the inner button of `add-to-cart-button` at 1024 px and wider and `purchase-cta` inside `purchase-rail` below it.

Scenario 1.2 uses a storage filter rather than a boolean one, because a storage filter's match is visible on every card's variant line ("256 GB") while a 5G filter is not shown on a card at all.

One row is planned against the nearest behaviour the screen actually offers rather than the control the row implies. E058: "Attempt mutation then Retry" → "Prior cart retained; error recovery does not duplicate item." The cart screen offers no quantity control at all - the line's quantity is read-only text (`cart-line-quantity`, "<n> db") and the storefront never issues `PATCH /api/v1/cart/items/:variantId`, so `?mi-scenario=fail-once-cart-quantity` never fires - and the cart screen's own mutations, removing the line with `cart-line-remove` ("Törlöm") and clearing the cart with `cart-clear` ("Kosár ürítése"), are covered by the sticky `cart-mutation-fails` scenario, which answers every attempt with 503 and so offers no recovery. Scenario 1.4 therefore drives `?mi-scenario=fail-once-cart-add` from the product page, whose refusal banner carries no retry control of its own: pressing the add control again IS the retry, and the once-only fault makes it succeed.

## Test Scenarios

### 1. Shop: retry after one failure

**Seed:** `e2e/seed.spec.ts`

#### 1.1. [E021] the featured phones come back after one failed load

**File:** `e2e/integration/shop-retry-featured-after-fail.spec.ts`

**Steps:**

1. Open the home page with the once-only product-list fault on the first load: `/` with `?mi-scenario=fail-once-products`, and wait for the hero to render. - expect: `hero-heading` is visible, so the home page itself is intact and only the featured row is broken. - expect: `featured-section` shows `error-state` with role `status`, whose title reads exactly "A kiemelt termékek nem tölthetők be" and whose message reads exactly "Ismeretlen hiba a termék betöltése közben.". - expect: The state's retry control `retry-button` reads "Újrapróbálom". - expect: No `featured-grid` and no `featured-card-*` element is rendered, and no `price-amount` is rendered anywhere on the page, so no price is fabricated while the list fails.
2. Press the inner button of `retry-button` ("Újrapróbálom"). - expect: The featured row re-requests the list and recovers: `error-state` and `retry-button` are gone from `featured-section` and `featured-grid` is rendered (the four skeletons `featured-card-skeleton-0` … `featured-card-skeleton-3` may show while the request runs). - expect: `featured-grid` holds exactly four `featured-card-*` cards, each with a non-empty name heading. - expect: Their "Egyszeri készülékár" `price-amount` values read "89 990", "69 990", "599 990" and "699 990", each with its separate "Ft" glyph beside it. - expect: The hero is unchanged: `hero-heading` is still visible and `featured-all-link` ("Összes telefon") is still offered under the row.

#### 1.2. [E030] the filtered catalogue comes back after one failed load

**File:** `e2e/integration/shop-retry-catalogue-after-fail.spec.ts`

**Steps:**

1. Open the catalogue with one filter already in the address and the once-only product-list fault on the first load: `/telefonok` with `?storageGb=256&mi-scenario=fail-once-products`, and wait for the error state. - expect: The `h1` reads "Mobiltelefonok". - expect: `result-count` reads exactly "A katalógus betöltése nem sikerült.". - expect: `catalog-error` holds `error-state` with role `alert`, titled "Nem sikerült betölteni a katalógust.", with the message "Ismeretlen hiba a katalógus betöltése közben." and a button reading "Újrapróbálom" (the catalogue's error state carries no `retry-button` test id of its own). - expect: No `product-card` is rendered. - expect: The filter the address names is preserved: the address still carries `storageGb=256`, `applied-filters` shows one `applied-chip` reading "256 GB" with `applied-chip-remove-storage`, and `filter-trigger` reads "Szűrők (1)". - expect: The storage facet is still selected where the viewport shows it: `filter-storage-256` carries `aria-pressed="true"` at 1024 px and wider, and `drawer-storage-256` does after opening the drawer with `filter-trigger` below 1024 px.
2. Press the "Újrapróbálom" button inside `catalog-error`'s `error-state`. - expect: The list re-requests and recovers: `error-state` is gone from the page and `result-count` reads "27 találat a szűrt feltételek szerint". - expect: 12 `product-card` elements are rendered. - expect: Every visible card matches the filter: each card's variant line ends with "256 GB". - expect: Every visible card's "Egyszeri készülékár" `price-amount` is a non-zero number; the first page's values are "89 990", "599 990", "549 990", "372 990", "319 990", "235 990", "471 990", "566 990", "457 990", "103 990", "167 989", "561 990", so no card is priced at zero. - expect: The filter is unchanged: the address still carries `storageGb=256` and `mi-scenario=fail-once-products`, the `applied-chip` still reads "256 GB", `filter-trigger` still reads "Szűrők (1)", and the storage facet still carries `aria-pressed="true"` where the viewport shows it.

#### 1.3. [E043] the product page comes back on the same variant after one failed load

**File:** `e2e/integration/shop-retry-product-after-fail.spec.ts`

**Steps:**

1. Open the catalogue with the once-only single-product fault on the first load: `/telefonok` with `?mi-scenario=fail-once-product`, and wait for the grid. - expect: The catalogue loads normally, because only the single-product endpoint is broken: `result-count` reads "<n> találat a szűrt feltételek szerint" with n greater than 0. - expect: 12 `product-card` elements are rendered.
2. Click the `product-card-cta` of the first `product-card` that carries no `product-card-stock` marker, and wait for the product page to settle. - expect: The address bar moves to that card's product page and carries its slug and its variant: `/telefonok/<slug>?variant=<slug>--<colour>-<storage>`. The in-app navigation drops `mi-scenario` from the address bar, but the mock keeps the fault for this browsing context. - expect: `product-loading` gives way to `error-state` with role `alert`, titled exactly "A termék nem tölthető be". - expect: The message reads "Ismeretlen hiba a termék betöltése közben." and the hint "A korábban megadott értékeket megőrizzük." (`error-hint`) is shown under it, and the state's button reads "Újrapróbálom". - expect: `product-name`, the gallery, the "Készülékár" price block, `add-to-cart-button` and `purchase-rail` are not rendered, and `related-products` is not rendered either, so no price is fabricated while the product is missing. - expect: Note the exact address (the `<slug>` and the `?variant=` value) for the next step; it is read from the address bar rather than pinned in the test.
3. Press "Újrapróbálom" inside the product page's `error-state`. - expect: The product is requested again and recovers: `error-state` is gone and `product-page` shows the product. - expect: The address bar is unchanged: the same `<slug>` and the same `?variant=<slug>--<colour>-<storage>`, so the shopper stays on the product they asked for. - expect: `product-name` is non-empty and reads that product's name, `product-stock` reads "Raktáron a demó készletben", and the "Készülékár" `price-amount` is a readable non-zero amount (for the first card this is "89 990"). - expect: The variant the address named is the one selected: the `variant-color-group` legend reads "Szín: <colour>" and that colour's button carries `aria-pressed="true"`, and the `variant-storage-group` legend reads "Tárhely: <n> GB" and that size's button carries `aria-pressed="true"` - the colour name and the storage size the address's `variant` carries (for the first card, "Szín: Zöld" and "Tárhely: 256 GB"). - expect: `related-products` and the visible add control (`add-to-cart-button` at 1024 px and wider, `purchase-cta` inside `purchase-rail` below 1024 px) are rendered again.

#### 1.4. [E058] the cart keeps its line and the retried add joins the same line

**File:** `e2e/integration/shop-retry-cart-add-after-fail.spec.ts`

**Steps:**

1. Open the catalogue with the once-only add fault on the first load: `/telefonok` with `?mi-scenario=fail-once-cart-add`, and wait for the grid. Open the first `product-card` that carries no `product-card-stock` marker through its `product-card-cta`, read `product-name` (call it the phone) and the digits of its "Készülékár" `price-amount` (call it P), then press the add control of the mount the viewport shows once: the inner button of `add-to-cart-button` at 1024 px and wider, `purchase-cta` inside `purchase-rail` below 1024 px. - expect: A visible `status-message` with role `alert` appears reading exactly "A termék hozzáadása nem sikerült; a kosár változatlan." with a "Bezárás" button: the first add of the page load was refused by the once-only fault. - expect: The banner carries no retry control of its own, so pressing the add control again IS the retry. - expect: The cart is untouched and the product page shows no `error-state`: `cart-badge` in the shop header reads "0".
2. Press the same add control again to retry. - expect: The confirmation `status-message` reads "<phone name>, <colour>, <n> GB – 1 darab a kosárban." with a "Bezárás" button. - expect: `cart-badge` reads "1": the retry added the phone exactly once, so the cart now holds one line at quantity 1.
3. Arm the fault again while the cart stays: `page.goto('/telefonok?mi-scenario=fail-once-cart-add')`, then open the same phone's product page again through the `product-card-cta` of the card whose `product-name` is the phone read in step 1, and press the add control of the mount the viewport shows once more. - expect: `cart-badge` still reads "1" before the press, because the same scenario name keeps the same cart across the page load. - expect: The add is refused again: the same `status-message` with role `alert` reads "A termék hozzáadása nem sikerült; a kosár változatlan." and `cart-badge` still reads "1", so the refused mutation changed nothing.
4. Check the prior cart is retained: click the header's `cart-link`. - expect: `cart-page` is visible with exactly one `cart-line`, its `cart-line-name` the phone's name and its `cart-line-quantity` "1 db". - expect: That line's "Részösszeg" `price-amount` reads P, `order-summary-subtotal`'s `price-amount` reads P, and `order-summary-total` still shows the "Végösszeg" placeholder ("—" with "Nincs megjeleníthető ár."): the previous line, quantity and total are all unchanged. - expect: `cart-count` reads "Kosárban található termékek (1)" and no second `cart-line` exists. - expect: `cart-badge` is not rendered on this screen, because the cart renders under the checkout header; the badge is read on a shop screen.
5. Retry the refused add: press the browser's Back to return to the phone's product page (in-app, no page load), then press the add control of the mount the viewport shows once more. - expect: The confirmation reads "<phone name>, <colour>, <n> GB – 2 darab a kosárban.". - expect: `cart-badge` reads "2", and it is read here on the shop screen because the cart screen carries none.
6. Open the cart with the header's `cart-link`. - expect: The cart holds exactly one `cart-line` - the phone - with `cart-line-quantity` "2 db" and its "Részösszeg" `price-amount` reading 2×P: the same variant is not listed twice, so the recovery did not duplicate the item. - expect: `cart-count` reads "Kosárban található termékek (1)" and `order-summary-subtotal`'s `price-amount` reads 2×P. - expect: The header badge read in the previous step ("2") matches the line's "2 db".
