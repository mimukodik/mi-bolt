# MiBolt checkout lost-answer test plan

## Application Overview

MiBolt is a Hungarian demo storefront: an Angular application served from the Playwright base URL with the in-page MSW mock behind it (no backend, no database). This plan covers the three paths where the server commits the order or the payment intent and the answer is lost on the way back, so the screen reports a failure over a write that has already landed. The purchase path is the phone listing `/telefonok`, the product page `/telefonok/<slug>`, the cart `/penztar/kosar` and the checkout wizard `/penztar/adatok` -> `/penztar/szallitas` -> `/penztar/ellenorzes` -> `/penztar/siker/<orderId>`; a card payment leaves the SPA for the demo payment application under `/demo-fizetes/<paymentIntentId>` and returns through `/penztar?paymentIntentId=...`. The checkout's permanent service faults are `specs/checkout-fault-paths.md`, and the happy paths, the cart and the payment round trip are `specs/storefront-integration.md`; no scenario from either is repeated here.

Three facts govern every scenario. First, each test starts in a fresh browser context and the mock keeps its state (cart, checkout draft, payment intents, receipts) in that context's `sessionStorage` under a key carrying the scenario name, and the MSW projects start signed in, so one fresh context is an empty cart and the scenarios are independent and can run in any order. Second, the mock reads `?mi-scenario=<name>` when the document loads and the MSW worker starts once per document: an in-app navigation keeps the scenario although the address bar loses the query, while a `page.goto` without the query loads the default scenario and a different, empty cart, so a fault spec opens its first page with the query and keeps it on every `page.goto` (rule 12 of `e2e/seed.spec.ts`). Third, `?mi-scenario=lost-once-order` and `?mi-scenario=lost-once-payment-intent` let the first order or payment-intent request of a page load run in full — the store commits and persists — and then replace that committed answer with a network error, as a timeout after commit looks; a later request with the same `Idempotency-Key` reads the stored result back, and a lost response arms again on every `page.goto` that keeps the query, because each page load builds a new handler list, while a retry inside the page does not.

Products are never named by slug or product name: every scenario picks its card by what the screen shows — the first card with no "Elfogyott" marker, whose price is at most 300 000 Ft for the two cash-on-delivery scenarios (the mock's cash-on-delivery ceiling). Controls built on the `app-button` primitive are host elements carrying the test id, so a press targets the native `button` inside them: `page.getByTestId('<id>').getByRole('button')`. Prices come from the `app-price-block` primitive, whose digits sit in `price-amount` with the `Ft` glyph as a separate span beside them, so a price is read as a number from that element. The two card steps need the demo payment application served on the port the shop's dev server proxies `/demo-fizetes` to (4210 in `angular.json`).

Widths: the integration projects run at 1920x1080, 1440, 1024, 768, 390x844 and 320, in Chromium, Firefox and WebKit. Below 1024 px the product page's purchase rail (`purchase-rail`, with `purchase-cta` and `purchase-rail-reason`) replaces the side panel's `add-to-cart-button`, and the confirmation of an add appears inside the rail instead of beside the button; every other control these scenarios touch carries the same test id at every width (checked at 390x844 and 1280x900).

Where a row asks for something no screen offers, the scenario records what the screen does instead, and no control is invented.

- (E064) "Commit silently then Retry same request" -> "Same DEMO number, same total, stock decremented once." The DEMO number and the total are on the receipt (`receipt-order-number`, `receipt-row-total`), and the number also carries the count, because it is the session's order counter — a second committed order would read "DEMO-000002". "Stock decremented once" has no screen surface: the screen's whole stock vocabulary is the availability sentence `product-stock` ("Raktáron a demó készletben" / "Ez a konfiguráció elfogyott a demó készletből.") and the card's `product-card-stock` marker ("Elfogyott"), there is no stock number anywhere, and after the single committed order the ordered variant was measured still in stock with its `maxQuantity` unchanged. The check this scenario makes is therefore the availability one: reopened after the order, the same variant still reads "Raktáron a demó készletben" and its card still carries no marker.
- (E065) "Reload before receipt then recover" -> "Replay/lookup receipt without contact persistence or second order." The reload offers no replay and no lookup: once the answer is lost the order id exists nowhere on the client, and the reload lands on the empty cart with `navigation-reason` reading "A kosarad üres, ezért ide irányítottunk.", from which no step of the wizard is reachable. The scenario follows what the screen does offer — the catalogue through "Telefonokat nézek" — and records that the row's replay/lookup has no control, while "without ... second order" is what the empty cart and the refused review step show. Nothing about the contact's persistence is asserted, because the contact step is not rendered after the reload.
- (E096) "Retry original payment key" -> "Intent not duplicated; correct existing state recovered." "Correct existing state recovered" is on screen: the payment page opens for the review's own total, on the intent the first press created, and the approved payment returns the review to "A fizetés jóváhagyva.". "Intent not duplicated" has no screen surface — neither the shop nor the demo payment application shows how many intents exist, and the first press never opens a payment page, so there is no earlier address to compare the second one with — so the scenario measures it beyond the screen: the retry carries the same non-empty `Idempotency-Key` as the first press, so the mock replays the intent the first press created rather than committing a second one, and the mock's own sessionStorage snapshot holds exactly one payment intent, the id the payment page names.

## Test Scenarios

### 1. Checkout: an answer lost after the commit

**Seed:** `e2e/seed.spec.ts`

#### 1.1. [E064] a retried order after a lost answer gives the same DEMO number

**File:** `e2e/integration/checkout-lost-order-retry.spec.ts`

**Steps:**

1. Open `/telefonok?mi-scenario=lost-once-order` and wait for the grid (`catalog-grid` with a `product-card`). - expect: `result-count` reads "55 találat a szűrt feltételek szerint" and 12 `product-card` elements are rendered. - expect: The first card carries no `product-card-stock` marker (no "Elfogyott"), shows a name, a colour and "<n> GB", and its "Egyszeri készülékár" block reads 89 990 with the "Ft" glyph as a separate span beside the digits. - expect: That card is the one every step below uses: it is the first card at or below 300 000 Ft (the mock's cash-on-delivery ceiling), so the delivery step can offer "Utánvét".
2. Open it through that card's `product-card-cta` ("Megnézem"). - expect: `product-page` is visible, `product-stock` reads "Raktáron a demó készletben" and the "Készülékár" block reads 89 990. - expect: Note the stock sentence and the price: step 10 reads the same screen again after the order.
3. Add the variant with the control the width shows: at 1024 px and wider the inner button of `add-to-cart-button` ("Kosárba teszem"); below 1024 px the inner button of the `purchase-rail` element `purchase-cta` (also "Kosárba teszem"). - expect: The confirmation appears — beside the button at 1024 px and wider, inside `purchase-rail` below it — reading "<the card's name>, <colour>, <n> GB – 1 darab a kosárban." - expect: The screen the width does not show renders nothing of the purchase controls: below 1024 px `add-to-cart-button` is not rendered, at 1024 px and wider no `purchase-rail` is shown.
4. Open the cart with the header's `cart-link` and read the page. - expect: `cart-page` is visible with exactly one `cart-line`, `cart-line-quantity` reads "1 db" and `cart-count` reads "Kosárban található termékek (1)". - expect: The checkout layout carries no `cart-badge` but does carry the step indicator `checkout-steps`.
5. Press `cart-continue` ("Tovább az adatokhoz"), fill the contact step with "Teszt Elek", "teszt@example.test" and "+36 30 123 4567", and press the inner button of `contact-submit` ("Tovább a szállításhoz"). - expect: `contact-page` is visible first and its `h1` reads "Kapcsolattartási adatok". - expect: The wizard advances: `delivery-step` is visible on `/penztar/szallitas` and its `h1` reads "Átvétel és fizetés".
6. On the delivery step choose "Házhoz szállítás" by its `delivery-radio`, fill "1052", "Budapest" and "Fő utca 1." into `address-input-postalCode`, `address-input-city` and `address-input-line1`, keep the "A számlázási cím megegyezik a szállítási címmel" tick (`billing-same-as-delivery`), choose "Utánvét" by its `payment-radio` and press the inner button of `delivery-confirm` ("Tovább az ellenőrzéshez"). - expect: `review-page` is visible on `/penztar/ellenorzes` and its `h1` reads "Minden rendben?". - expect: `review-payment` reads "Utánvét", `review-delivery` reads "Házhoz szállítás", `review-items` lists one `review-line` whose `review-line-quantity` reads "1 × 89 990 Ft", and `review-summary` shows Részösszeg 89 990, Szállítási díj 0, Fizetési díj 490 and Végösszeg 90 480. - expect: Note the Végösszeg the summary shows (90 480 Ft): step 8 checks the receipt against it.
7. Tick `review-consent-terms-input` ("Elfogadom a demó rendelési feltételeit.") and press the inner button of `review-submit` ("Demórendelés véglegesítése") once: this is the row's "Commit silently", where the order commits and its answer is lost on the way back. - expect: The browser stays on `/penztar/ellenorzes` and `order-receipt` is not rendered. - expect: `review-submit-failure` is rendered, its `data-error-code` reads "UNKNOWN", its sentence reads "A kosarad és az adataid megmaradtak. Próbáld újra, vagy módosítsd a fizetési módot." and it carries a "Fizetési mód módosítása" control (`review-change-payment`). - expect: `review-state-banner` reads "A rendelés leadása nem sikerült.". - expect: Nothing is lost on screen: one `review-line` is still listed, `review-summary` is still rendered, `review-contact` still shows "Teszt Elek", "teszt@example.test" and "+36301234567", and the terms tick is still checked.
8. Press the inner button of `review-submit` again ("Retry same request"). - expect: The browser lands on `/penztar/siker/<orderId>` and `order-receipt` is visible: the retry took the replayed receipt of the order the first press committed. - expect: `success-heading` reads "Elkészült a demórendelésed.", `success-check` is rendered and `receipt-demo-badge` reads "DEMO". - expect: `receipt-order-number` reads "DEMO-000001" — the first value of the session's own order counter, which is the screen's statement that exactly one order was created, since a second committed order would read "DEMO-000002". - expect: `receipt-row-total` reads 90 480, equal to the Végösszeg noted on the review page, and `receipt-row-payment` reads "Utánvét". - expect: `receipt-lines` lists exactly one `receipt-line`, reading the ordered product with its colour and storage, "1 db" and "89 990 Ft". - expect: `receipt-row-status` reads "Demó rendelés visszaigazolva" and `receipt-simulation-notice` reads "Demó figyelmeztetés. A demórendelés elkészült. Nem történt valódi fizetés, rendelésküldés vagy e-mail-küldés.".
9. Check that the single order closed the cart and that no second one can be placed: open `/penztar/kosar?mi-scenario=lost-once-order` as a fresh page load (every `page.goto` keeps the query, per rule 12 of `e2e/seed.spec.ts`), then open the review step the same way at `/penztar/ellenorzes?mi-scenario=lost-once-order`. - expect: `cart-page` shows its empty state: no `cart-line`, the title "A kosarad még üres.", the message "Nézd meg a demókészülékeket, és válaszd ki a kedvenced." and the action "Telefonokat nézek". - expect: The review step is not reachable from this state: the browser lands on `/penztar/kosar?navigationReason=empty-cart` with `cart-page` visible, `navigation-reason` reading "A kosarad üres, ezért ide irányítottunk." and no `review-page`, so the one committed order cannot be placed a second time.
10. Check the phone's stock by what the screen can show: reopen the ordered variant's product page and the catalogue with the query kept (`/telefonok/<slug>?variant=<id>&mi-scenario=lost-once-order` and `/telefonok?mi-scenario=lost-once-order`) and read the stock statements the screen carries. - expect: `product-stock` still reads "Raktáron a demó készletben" and the same card still carries no `product-card-stock` marker, so nothing the screen shows has changed after the one committed order. - expect: The screen carries no stock number anywhere: `product-stock` and `product-card-stock` are its whole stock vocabulary, so the row's "stock decremented once" has no screen surface — the check this scenario makes is that the ordered variant is still shown in stock after the single order.

#### 1.2. [E065] a reload before the receipt lands on the empty cart, not on a replayed receipt

**File:** `e2e/integration/checkout-lost-order-reload.spec.ts`

**Steps:**

1. Reach the review step with a cash-on-delivery draft under the fault: open `/telefonok?mi-scenario=lost-once-order`, open the first `product-card` that has no `product-card-stock` marker and whose `price-amount` is at most 300 000 Ft through its `product-card-cta`, add it (the inner button of `add-to-cart-button` at 1024 px and wider, the inner button of the `purchase-rail`'s `purchase-cta` below 1024 px), open the cart with `cart-link`, press `cart-continue`, fill the contact step with "Teszt Elek", "teszt@example.test" and "+36 30 123 4567" and press `contact-submit`, then on the delivery step choose "Házhoz szállítás", fill "1052" / "Budapest" / "Fő utca 1.", choose "Utánvét" by its `payment-radio` and press `delivery-confirm`. - expect: `review-page` is visible on `/penztar/ellenorzes` with one `review-line`, `review-payment` reading "Utánvét" and `review-summary` showing Végösszeg 90 480. - expect: Note the Végösszeg, because it is the total the lost order committed with.
2. Tick `review-consent-terms-input` and press the inner button of `review-submit` ("Demórendelés véglegesítése") once. - expect: `review-submit-failure` is rendered with `data-error-code` "UNKNOWN" and the sentence "A kosarad és az adataid megmaradtak. Próbáld újra, vagy módosítsd a fizetési módot.", and `review-state-banner` reads "A rendelés leadása nem sikerült.". - expect: The browser stays on `/penztar/ellenorzes` and `order-receipt` is not rendered, so the order is committed and its answer is gone.
3. Reload the review page instead of retrying, keeping the scenario: `page.url()` carries `/penztar/ellenorzes` without the query, so the reload names the URL with it — `page.goto(`${page.url()}?mi-scenario=lost-once-order`)`. - expect: The wizard does not re-render the review: the browser lands on `/penztar/kosar?navigationReason=empty-cart` with `cart-page` visible and `review-page` not rendered. - expect: `navigation-reason` reads "A kosarad üres, ezért ide irányítottunk." with a "Bezárás" control. - expect: The cart is empty: no `cart-line`, the title "A kosarad még üres.", the message "Nézd meg a demókészülékeket, és válaszd ki a kedvenced." and the action "Telefonokat nézek" — the commit emptied the cart and cleared the draft, and the new page load cannot read either back. - expect: No `order-receipt` and no `receipt-order-number` are rendered anywhere on the page.
4. Read what the reloaded screen offers to recover, and what it does not offer. - expect: The reloaded page carries no submit control at all: no `review-submit`, no `review-payment-new`, no order id and no control that looks an order up, so the row's "Replay/lookup receipt" has nothing to press here — the order's id only ever existed in the answer that was lost. - expect: The reload's own statement is the empty cart, so the fault (`lost-once-order`) re-arms on this page load without a request to lose: there is no earlier step in this new load that could commit a second order. - expect: What the screen does offer is its way out: the action "Telefonokat nézek" leads to `/telefonok` with the catalogue grid rendered. - expect: Nothing on this screen names the contact that was typed, since no checkout step is rendered on it; the contact's persistence across the reload is deliberately not asserted.
5. Check that no second order can come of the reloaded state: open `/penztar/ellenorzes?mi-scenario=lost-once-order` as a fresh page load. - expect: The same landing: `/penztar/kosar?navigationReason=empty-cart` with `cart-page` visible, `navigation-reason` reading "A kosarad üres, ezért ide irányítottunk." and no `review-page`. - expect: This is the row's "without ... second order" in the only form the screen can show it: the cart holds no lines and the wizard refuses every step past it, so the reloaded session can place no order at all.

#### 1.3. [E096] a retried payment start opens the payment page for the intent the first press created

**File:** `e2e/integration/checkout-lost-intent-retry.spec.ts`

**Steps:**

1. Reach the review step with a card draft under the fault: open `/telefonok?mi-scenario=lost-once-payment-intent`, open the first `product-card` that has no `product-card-stock` marker through its `product-card-cta`, add it (the inner button of `add-to-cart-button` at 1024 px and wider, `purchase-cta` below 1024 px), open the cart with `cart-link`, press `cart-continue`, fill the contact step with "Teszt Elek", "teszt@example.test" and "+36 30 123 4567" and press `contact-submit`, then on the delivery step choose "Házhoz szállítás", fill "1052" / "Budapest" / "Fő utca 1.", choose "Bankkártya" by its `payment-radio` (value `card`) and press `delivery-confirm`. - expect: `review-page` is visible on `/penztar/ellenorzes`, `review-payment` reads "Bankkártya" and `review-payment-status` reads "A kártyás fizetéshez indítsd el a fizetést.". - expect: `review-payment-new` is rendered with the label "Fizetés indítása", the inner button of `review-submit` is disabled and `review-cta-explanation` reads "A kártyás fizetés jóváhagyása szükséges a rendelés leadásához.". - expect: `review-items` lists one `review-line` and `review-summary` shows Fizetési díj 0 and Végösszeg 89 990; note that Végösszeg, because it is the amount the payment is checked against in step 3.
2. Press the inner button of `review-payment-new` ("Fizetés indítása") once: the intent commits and its answer is lost on the way back. - expect: The browser stays on `/penztar/ellenorzes`: no navigation to `/demo-fizetes/` happens. - expect: `review-submit-failure` is rendered with `data-error-code` "UNKNOWN" and the sentence "A kosarad és az adataid megmaradtak. Próbáld újra, vagy módosítsd a fizetési módot." beside a "Fizetési mód módosítása" control, and `review-state-banner` reads "A rendelés leadása nem sikerült.". - expect: The payment branch is unchanged and still reads "A kártyás fizetéshez indítsd el a fizetést." with its "Fizetés indítása" control, so the screen says no payment exists although one was created. - expect: The inner button of `review-submit` is still disabled, one `review-line` is still listed and `review-summary` is still rendered.
3. Press the inner button of `review-payment-new` again (the row's "Retry original payment key") and read the demo payment page it opens. - expect: The browser leaves the shop: the URL is `/demo-fizetes/<paymentIntentId>` with the intent id as its last path segment. - expect: The page's `h1` reads "Fizetés jóváhagyása" and its lede reads "Ez egy szimulált fizetési felület. Válaszd ki, hogyan viselkedjen a fizetés.". - expect: `pay-amount` reads 89 990 Ft, equal to the Végösszeg noted on the review page, and `pay-ref` reads the same id the address bar carries. - expect: The three outcome controls are visible: "Sikeres fizetés" (`pay-succeeded`), "Elutasított fizetés" (`pay-declined`) and "Függőben marad" (`pay-pending`). - expect: The row's "Intent not duplicated" has no screen surface — neither the shop nor the demo payment application shows how many intents exist, and the first press never reached a payment page, so there is no earlier address and no earlier `pay-ref` to compare this id with — so it is measured beyond the screen: exactly two `POST` requests to `/api/v1/payment-intents` are recorded for the scenario, both carrying the same non-empty `Idempotency-Key`, and the mock's own sessionStorage snapshot (`mi-bolt.snapshot.lost-once-payment-intent`) holds exactly one payment intent, the id this payment page names.
4. Press `pay-succeeded` ("Sikeres fizetés") and read the return to the shop. - expect: The browser returns to the shop: the return URL is `/penztar?paymentIntentId=<id>` and the cold-start page navigates on to the review step, so `review-page` is visible on `/penztar/ellenorzes`. - expect: `review-payment-status` reads "A fizetés jóváhagyva." and the inner button of `review-submit` is enabled. - expect: The terms tick is not carried here: `review-consent-terms-input` is unchecked and `review-cta-explanation` reads "A demó feltételek elfogadása szükséges a leadáshoz.".
5. Tick `review-consent-terms-input` ("Elfogadom a demó rendelési feltételeit.") and press the inner button of `review-submit` ("Demórendelés véglegesítése"). - expect: The browser lands on `/penztar/siker/<orderId>` and `order-receipt` is visible. - expect: `success-heading` reads "Elkészült a demórendelésed." and `receipt-order-number` reads "DEMO-000001" — one order, the first value of the session's order counter. - expect: `receipt-row-total` reads 89 990, equal to the amount the demo payment page showed, and exactly one `receipt-line` is listed. - expect: `receipt-row-payment` reads "Bankkártya" and `receipt-row-status` reads "Demó rendelés visszaigazolva".
