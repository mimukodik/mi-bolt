# 0012 — Payment intents, idempotency replay, and order placement

## Situation

T7 ships the five operations of `/payment-intents*` and `/orders*` on top
of the T6 checkout draft and the T5 cart: `POST /payment-intents`,
`GET /payment-intents/{paymentIntentId}`,
`POST /payment-intents/{paymentIntentId}/outcome`, `POST /orders`,
and `GET /orders/{orderId}`. `docs/02-backend.md` §4.4–4.6
(rules 30–47) fix the behaviour (intent ids are opaque, intents expire
lazily, outcomes are one-shot, idempotency replay runs before every
other check, the whole order is one transaction), and `docs/01`
§4 and §8.3 plus `docs/04` §4 fix the storage shape. The contract
declares two response shapes (`PaymentIntent`, `OrderReceipt`) and an
`OrderRequest` discriminated by `paymentMethod`. The fee numbers, the
intent lifetime and the URL prefixes are not in the contract; the
implementation picks them and records the choice here.

## Decision

- **Intent id.** A `UUID.randomUUID()` string, opaque to the client,
  carried on the URL and on the receipt. No enumeration is exposed.
- **Order id.** The numeric primary key of the `shop_order` row,
  rendered as a decimal string. `{orderId}` in the contract addresses
  it. A non-numeric `orderId` answers 404 (rule 45).
- **Order number.** `DEMO-` followed by six random decimal digits,
  generated by `OrderService.uniqueOrderNumber` with a uniqueness
  retry; collisions are rare and the loop ends on the first miss
  (rule 46).
- **Idempotency scope.** `(session, method, path, idempotencyKey)`.
  The four-tuple is the unique key on `idempotency_record` and the
  lookup tuple on `replay`. A replay on `POST /payment-intents` is
  invisible to `POST /orders`: each endpoint owns its own scope
  (test: `sameKeyOnOrdersIsADifferentScope`).
- **Fingerprint.** `IdempotencyService.fingerprint` is hex SHA-256 of
  the body that Jackson produced by serialising the inbound object
  (or the empty string for `POST /payment-intents`, which carries no
  body). Key order and whitespace therefore do not matter for the
  "same body" comparison.
- **Stored response.** Only `201 Created` results are stored and
  replayed. The `Location` header, the status code and the JSON body
  land together; a `replayed(...)` re-serialises the stored body into
  the response DTO. A different body with the same key answers 409
  `IDEMPOTENCY_CONFLICT`.
- **Retention.** Records older than 24 hours (`mibolt.idempotency.retention`)
  are ignored on lookup; `replay` treats them as a fresh request and
  `store` purges any stale row before insert so the unique constraint
  does not trip. No purge job runs.
- **Replay before any check.** `IdempotencyService.replay` runs
  before `CartService.expectVersion`, before the price-and-stock
  reconciliation, and before the draft check. A retry after an
  uncertain response therefore returns the original receipt rather
  than a `412 CART_VERSION_CONFLICT` or a `422 CHECKOUT_INCOMPLETE`
  (rule 37).
- **Price or stock notice from the cart's reconciliation is answered
  with `409 PRICE_CHANGED` or `409 OUT_OF_STOCK` before the
  `If-Match` check**, so a real change never surfaces as 412
  (rule 47).
- **Lazy expiry.** A pending or unactioned intent flips to `declined`
  on the first read after `expiresAt`. `mibolt.payment.intent-lifetime`
  is 30 minutes. There is no scheduler; the flip happens inside
  `PaymentIntentService.get` and `resolve`.
- **One-shot outcome.** The outcome endpoint is reachable only from
  `requires_action`. A repeat call on a terminal intent answers 409
  `PAYMENT_ALREADY_RESOLVED`. A caller that lost the response reads
  with `GET /payment-intents/{id}` rather than calling again.
- **`termsVersion`.** Read from the concrete request type
  (`CardOrderRequest.termsVersion` or
  `CashOnDeliveryOrderRequest.termsVersion`). A missing or different
  value answers 422 with a `VALIDATION_FAILED` body and a contract-named
  field error.
- **One transaction.** `OrdersController.createOrder` and
  `PaymentIntentsController.createPaymentIntent` carry a method-level
  `@Transactional` (the read and outcome endpoints do not, so they run
  under `PaymentIntentService`'s own no-rollback rule); the service's
  class-level `@Transactional` joins into that one transaction
  with the idempotency `store`. A failure inside `orderService.place`
  (stock decrement returning 0, intent not `succeeded`, terms
  mismatch, ...) rolls back every write of the request: stock, the
  receipt, the idempotency record, the draft closure, the cart delete
  and the fresh cart insert (rule 42).
- **Expired cart on `POST /payment-intents`.** Answers 410
  `CART_EXPIRED` like every cart-bound write. The contract did not
  list the status for this operation until 2026-09-20, when the issue
  owner had it added (`api/openapi.yaml`, `responses/Gone`);
  `PaymentIntentsApiTest.expiredCartIs410` validates the response
  against it.
- **URL prefixes and the notice.** The intent's `redirectUrl` /
  `returnUrl` prefixes (`mibolt.payment.redirect-url-prefix`,
  `mibolt.payment.return-url-prefix`) are `application.properties`
  values, read by `@Value` in the services. The receipt's `notice`
  text is the Java constant `OrderService.NOTICE`, not a property:
  Spring reads `.properties` files as ISO-8859-1, so the accented
  Hungarian text arrived garbled when it was a property value.
- **Card order without `paymentIntentId`.** docs/02-backend.md rule 38
  calls the missing id a schema violation (400). Since T9b the shared
  `ProblemAdvice.handleBodyValidation` answers 400 `INVALID_REQUEST`
  whenever a `@NotNull` member is missing (field code `REQUIRED`) and
  422 `VALIDATION_FAILED` for a present but wrong value;
  `OrdersApiTest.cardOrderWithoutIntentIs400` pins it.
- **Cash-on-delivery order with `paymentIntentId`.** docs/02-backend.md
  rule 39 says the member does not exist on such an order. Since T9c
  `spring.jackson.deserialization.fail-on-unknown-properties=true` makes
  Jackson refuse any member a request schema does not declare, and
  `ProblemAdvice.handleUnreadable` answers 400 `INVALID_REQUEST`;
  `OrdersApiTest.codOrderWithIntentIdIs400` pins it.
- **`idempotency_record.response_body` is `varchar(20000)`.** 0005 declared
  it `clob`, which PostgreSQL creates as `text` while the entity's `@Lob
  String` expects `oid` since Hibernate 5.6.2, so schema validation refused
  to start the application on PostgreSQL; H2 creates a `CLOB` and matched,
  which is why every test and CI stayed green. Changeset 0006 (T11,
  2026-09-20) changes the column to `varchar(20000)` on every database and
  the entity maps it as a plain length-limited string. The receipt JSON is a
  few KB.

The fees and thresholds are configuration under
`mibolt.payment.*` and `mibolt.checkout.*` (`application.properties`):

| Property                              | Value                                                          |
| ------------------------------------- | -------------------------------------------------------------: |
| `mibolt.payment.intent-lifetime`      | `30m`                                                          |
| `mibolt.payment.redirect-url-prefix`  | `http://localhost:4210/demo-fizetes/` (env `MIBOLT_PAYMENT_REDIRECT_URL_PREFIX`) |
| `mibolt.payment.return-url-prefix`    | `http://localhost:4200/penztar?paymentIntentId=` (env `MIBOLT_PAYMENT_RETURN_URL_PREFIX`) |
| `mibolt.idempotency.retention`        | `24h`                                                          |

**The URL prefixes, the 30-minute lifetime and the 24-hour retention
were chosen on 2026-09-20 as demo defaults and accepted by the issue
owner the same day; changing them is a properties edit.** A future
issue that wants different numbers edits `application.properties` and
adds a comment pointing at this record.

**Since MIM-251 (2026-09-22) both URL prefixes are absolute and
environment-overridable.** The demo payment app is a separate origin
(port 4210 by default), like a real payment gateway; the shop navigates
to `redirectUrl` and the payment app back to `returnUrl` with full page
loads, so the backend has to name the host in both. The relative
defaults recorded above held until that date. `scripts/demo-stack.sh`
derives the two environment variables from its port settings (the demo
stack unit of the same issue, merged right after this one).

## Consequences

- No scheduler, no purge job. A new intent needs a new
  `Idempotency-Key`; a declined intent needs a new intent and a new
  key.
- The controller layer does no business validation. Every rule lives
  in `PaymentIntentService` or `OrderService`; the controllers only
  replay, store, and map the result to a DTO. The brief
  intentionally re-implements `json()` and `replayed()` in both
  controllers rather than introducing a third class, because the
  duplication is two short methods and the abstraction would carry
  no extra behaviour.
- `CheckoutModels.toAddress` is `public static` so `OrderModels` can
  build the same `Address` for an order receipt without re-deriving
  the country-code enum mapping.
- Test counts after this unit are pasted in the `README.md` `Run`
  section; the JaCoCo `LINE` gate stays at the `build.gradle`
  defaults.
