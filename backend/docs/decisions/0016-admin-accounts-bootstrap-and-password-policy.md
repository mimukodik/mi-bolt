# 0016 — Admin accounts: first-admin bootstrap and password policy

## Situation

The admin API needs accounts. The owner wants the first admin and its
password printed to the output at first start, the way security-minded
products do, and the first admin's id is not the integer literal `1`.
There is no e-mail and no forced change at first sign-in (owner decisions
of 2026-09-22).

## Decision

### Bootstrap

`AdminBootstrap` (`admin/user/AdminBootstrap.java`, `ApplicationRunner`,
`@Order(1)`, after `CatalogLoader` at `@Order(0)`) runs once at startup
when `admin_user` is empty; on a non-empty table it logs at INFO and
returns. The username is fixed to `admin`. The password is taken from
`mibolt.admin.initial-password` (`MIBOLT_ADMIN_INITIAL_PASSWORD`) when
non-blank, otherwise generated by `PasswordGenerator`. The chosen value
is hashed by `PasswordEncoderFactories.createDelegatingPasswordEncoder()`
(bcrypt with the `{bcrypt}` prefix) and stored. A configured value
outside `PasswordPolicy` stops the start with `IllegalStateException`.

The two WARN lines are produced verbatim:

- generated password:
  `initial admin created: username=admin password=<pw> (shown once; change it after the first sign-in)`
- configured password:
  `initial admin created: username=admin password=<from MIBOLT_ADMIN_INITIAL_PASSWORD>`

A non-empty table logs at INFO:

- `admin users present, N, bootstrap skipped`

Ids are UUID v4, assigned by Hibernate (`@GeneratedValue(strategy =
GenerationType.UUID)`); the first admin's id is never `1`.

### Password policy

`PasswordPolicy.violations(String)` returns the field-error codes the
password breaks, length first, then bytes; an empty list means the value
is acceptable:

- 15 to 64 characters, no composition rules (NIST SP 800-63B-4
  §3.1.1.2, https://pages.nist.gov/800-63-4/sp800-63b.html).
- At most 72 UTF-8 bytes, bcrypt's input limit. Spring Security rejects
  longer input since CVE-2025-22228
  (https://spring.io/security/cve-2025-22228).
- A length violation is the code `SIZE`; a byte violation is
  `PASSWORD_TOO_LONG`.

### Generated passwords

`PasswordGenerator.generate()` reads 18 bytes from `SecureRandom` and
encodes them with `Base64.getUrlEncoder().withoutPadding()` → exactly 24
characters from `A-Z a-z 0-9 - _`, inside `PasswordPolicy`. The same
generator serves the users API's new admins.

### Users and own-password rules (the next units implement)

- The list is unpaged, ordered by `createdAt` then `username`.
- Username pattern `^[a-z0-9]+(?:[._-][a-z0-9]+)*$`, at most 80.
- Create returns the generated password once. A taken name is `409
  USERNAME_TAKEN`.
- Delete: the signed-in admin is `409 ADMIN_SELF_DELETE` (checked
  first); the last remaining admin is `409 LAST_ADMIN`; an unknown id is
  `404`.
- Own password change: a wrong current password is `422 /currentPassword
  WRONG_PASSWORD`; a new password over 72 bytes is `422 /newPassword
  PASSWORD_TOO_LONG` (length bounds come from the schema as `SIZE`). The
  session stays signed in.

## Consequences

- The generated password sits in the log once, so whoever reads the log
  can sign in until it is changed. CI and docker runs set
  `MIBOLT_ADMIN_INITIAL_PASSWORD`, and the log then names only the
  variable. The deployment guide (`docs/06-uzembe-helyezes.md` §4) shows
  the `docker logs … | grep 'initial admin'` line.
- Deleting every admin is impossible through the API (`LAST_ADMIN`), so
  the bootstrap runs again only on an emptied table.
